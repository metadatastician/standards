= Decision spec — `*.scorecard.a2ml` corpus (70+) → deed era (family 5)
Campaign: standards#837 · Frame: link:README.adoc[mappings/README] ·
Status: **RULED: option B** (owner, 2026-10-09, ruling R5 on standards#837).
For the RSR scorecard, R5 option B is superseded by the owner's ruling of
2026-11-14 (§6).
Increment 1 (§4 leak clean + archive) is done; increments 2 and 3 are
pending. See §5.
§6, the RSR scorecard clause, is RULED (owner, 2026-11-14, ratified with
`:assessor` and `:assessed-at`).

Scorecards are the wrong shape for the naïve "translate each file" move:
they are **time-stamped assessment records**, not repo state. Translating
them like descriptiles would mint dozens of mute permanent snapshots into
the coordination surface that repo deeds are.

== 1. Corpus shape (recon: standards repo, scorecard dir)

* One file per spec under test: `<spec_id>.scorecard.a2ml`.
* Header table: `spec_id`, `version`, `assessed_date`, `assessor` (the
  `assessor` is "estate-audit" — a TOOL IDENTITY, i.e. provenance
  metadata, not content).
* Repeated `[[must]]` / `[[should]]` / `[[could]]` arrays: per-criterion
  `id`, `text`, `system` (probe description), `status` (`pass|fail`),
  `evidence`, `check`, `effects`.
* Field spelling is snake_case at the header (`spec_id`, `assessed_date`)
  — GENUINE a2ml dialect difference from the descriptile families
  (kebab-case); the dialect split is recorded here so the translator's
  per-family normalisation is explicit, not discovered.

== 2. Options on the table

**A. Translate all 70+ into repo deeds** — bloat: a `(must …)` entry with
pass/fail for a moment in 2026 is a record; after one re-assessment there
are competing "latest" claims. Rejected in spec terms: repo-deed is a
current-state registry form (§251 of the grammar spec: order-free,
dedupe-free by design for state).

**B. Freeze corpus + current-verdict summary only (RECOMMENDED)** —
1. The 70+ historical files become an archive surface
   (`.machine_readable/archive/scorecards-v1/`) with a tombstone comment;
   the data is **not translated** — translation of time-series records is
   lossy by construction, and the archive preserves provenance verbatim.
2. ONE current snapshot per spec_id lands on the *assessed repo's* deed as
   `(assessment :spec accessibility :version "1.0.0" :date "2026-07-03"
   :assessor estate-audit :must-pass 2 :must-fail 2)` — aggregate counts
   only, never rows; row-level truth stays in the archive + auditor.
3. Future assessments are produced by estate-audit directly in the deeds
   era (tool PR rides separately) — the corpus stops accumulating v1s
   at the seam.

**C. New doc-head `scorecard-deed`** — grammar change, owner-ruling
territory by definition (grammar surface). Recorded so it is answered
once, not re-litigated per PR: NOT requested; the assessment-summary
clause + archive covers the need without expanding the four-head grammar.

== 3. Acceptance (once ruled)

* Zero live `*.scorecard.a2ml` outside the archive surface.
* Exactly one `(assessment …)` clause per previously-covered spec_id on
  the right repo deed; `:assessor` carried as SYMBOL (`estate-audit`).
* Archive tombstones link forward: each archived file names the repo deed
  that now carries its summary.

== 4. Remediation needing NO ruling: the absolute-path leak

While reconnning: `evidence` fields in the corpus contain absolute local
paths, e.g. `…/accessibility.scorecard.a2ml` cites
`/home/user/standards/.machine_readable/contractiles/adjust/Adjustfile.a2ml`.
Machine-local absolute paths in repo-committed assessment evidence are
(a) meaningless on any other machine, (b) a workstation-layout disclosure.

Because this is *fix-in-place data hygiene on files we are freezing anyway*,
it does NOT wait for the A/B ruling: the recommendation is a sed-level pass
over the corpus (only literal `/home/user/standards/` and equivalents →
repo-relative `…/`) **before** archiving, so the archive is clean from the
first day. Deliverable list of offending lines rides in the owner-side
residue ledger rather than being silently edited in a translation PR.
(Per closeout discipline: listed, evidence-attached, owner-visible — not
swept.)

== 6. The RSR scorecard (owner rulings 2026-11-14)

Status: *RULED* (owner, 2026-11-14; §6.4). Grammar:
`../spec/abnf/clauses/rsr-scorecard.abnf` v0.2.0. Checker:
`deed_lint.js --rsr-scorecard` (`../tools/README.adoc`).

The RSR oracle (Hypatia `RsrConformance`, run by `mix hypatia.rsr_score
--write` and by hypatia's reusable `rsr-oracle.yml` in every calling repo)
wrote `.machine_readable/scorecards/rsr.scorecard.a2ml` into each scored repo:
an estate-wide A2ML producer. The `(assessment …)` summary of §2 B.2 does not
fit it, because an RSR result is a tier, a weighted score and one verdict per
criterion, not must/should counts. The owner ruled on 2026-11-14 that RSR gets
a clause of its own, and that the writer switches to it.

=== 6.1 Where it lives

A scorecard is an assessment record. Under the three layers of the estate it
is not identity (the chora deed says what the repo *is*), not content
organisation (`CLADE.deed`), and not registry (chora-registry). So it is not
a clause of the chora deed, and §2 B.2's placement on the assessed repo's
deed is not followed for RSR. It is the one clause of its own file, the
pattern the proof receipt already set for the estate's other machine-written
verification record (PROOF-POLICY §8.5):

* a `praxis-deed` with `:profile rsr-scorecard`, at
  `.machine_readable/scorecards/rsr-scorecard_praxis.deed`;
* no new doc-head and no new file-name dispatch, so `deed.abnf` is unchanged
  (option C of §2 stays not requested). `rsr.scorecard.deed` would dispatch to
  nothing and be refused;
* the oracle overwrites the one file on each run, so there is one current
  scorecard and never competing "latest" claims (§2 A's objection). History
  is the file's git history.

=== 6.2 Shape

----
(praxis-deed
  :schema-version "1.0.0"
  :canonical-name "rsr-scorecard"
  :profile rsr-scorecard
  :beholding-chora #uuid"…"        ; optional: the scored repo's estate chora
  (rsr-scorecard
    :repo "hypatia"                ; the scored repo's :canonical-name
    :spec rsr-criteria-v2
    :spec-version "2.1.0-draft"    ; the catalogue's own version, verbatim
    :assessor "hypatia rsr_score 0.1.0" ; the tool that scored, and its version
    :assessed-at "2026-11-14T19:33:12Z" ; when it ran: RFC 3339, UTC
    :tier bronze                   ; none | bronze | silver | gold | rhodium
    :score "85.78"                 ; decimal string, derived (6.3)
    :provisional #t
    :automatable-coverage "0.71"
    :applicable-weight "61.1"      ; optional
    :verified-weight "43.3"        ; optional
    :profile-present #f            ; optional
    :source-commit "…40 hex…"      ; optional: the scored commit
    (criterion :id "1.1.2" :name "justfile" :tier bronze :gate "universal"
               :weight "1.6667" :verdict pass)
    …))
----

Every criterion the catalogue lists has one `(criterion …)`, `na` ones
included, so the record is complete and the denominators can be recomputed.

=== 6.3 Rules beyond the grammar

* *Derived, not asserted.* `:score` is 100 × (pass weight + half the partial
  weight) / (pass + partial + fail weight), and `:automatable-coverage` is
  that verified weight over every applicable weight (all verdicts but `na`).
  The checker recomputes both from the criteria and refuses a recorded value
  they do not give (tolerance 0.02 and 0.001, for the four-place rounding of
  the weights). The tier is not recomputed: its thresholds are the catalogue's.
* *No overclaim* (RSR-SPEC-v2 §10). Coverage below 1 needs `:provisional #t`,
  and a provisional scorecard is never `rhodium`.
* *Who and when.* `:assessor` and `:assessed-at` appear exactly once each.
  `:assessor` is not empty; it names the tool and its version, such as
  `"hypatia rsr_score 0.1.0"`. `:assessed-at` is the RFC 3339 date-time in
  UTC, written one way (`YYYY-MM-DDThh:mm:ssZ`: upper-case `T` and `Z`,
  whole seconds, no offset, no leap second), and its date is a real day.
* The `rsr.scorecard.a2ml` files already in repos are legacy. The writer no
  longer produces them; whether each is deleted or archived is the per-repo
  M7 PR's decision, not the writer's.

=== 6.4 Ruling: ratified with `:assessor` and `:assessed-at` (owner, 2026-11-14)

The owner ratified this design on 2026-11-14 (standards#1583), with one
change: `:assessor` and `:assessed-at` join the clause. The ruling settles
both questions this section left open in v0.1.0:

. *Ratified:* the `(rsr-scorecard …)` clause, and its placement as the one
  clause of a praxis-deed (6.1) in preference to a chora-deed clause or a new
  doc-head. It supersedes R5 option B (§5) for the RSR scorecard: an RSR
  result is not an `(assessment …)` summary on the assessed repo's own deed.
. *Closed:* the assessor and the date join the clause, required, once each
  (6.2, 6.3). v0.1.0 left them out so that an unchanged repo rescored gave a
  byte-identical file. With `:assessed-at` that no longer holds: each run
  writes a new time, and `:source-commit` still names what was scored.

`rsr-scorecard.abnf` v0.2.0 carries the change. It is not additive: a
v0.1.0 scorecard without the two fields is refused and is rewritten by
rescoring. The writer is Hypatia's `RsrConformance.to_deed/2`.
