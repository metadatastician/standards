IANA Media Type Registration: application/vnd.metadatastician.k9
================================================================
SPDX-License-Identifier: CC-BY-SA-4.0

This file is the canonical registration document for
application/vnd.metadatastician.k9.  It lives beside the specification
it registers; there is no second copy.

NOTE: Earlier drafts used "application/vnd.k9+nickel" but the +nickel
structured syntax suffix is not registered with IANA.  Per RFC 6838
Section 4.2.8, unregistered suffixes SHOULD NOT be used.  This
registration uses a base type with no suffix, now
"application/vnd.metadatastician.k9" (owner ruling I1, 2026-11-12).

FILING ORDER (owner ruling, 2026-11-12).  The three registrations are
filed one at a time, in this order:

  1. application/vnd.metadatastician.k9.coordination
  2. application/vnd.metadatastician.k9
  3. application/vnd.metadatastician.deed

Precondition: none is filed while its specification is marked DRAFT,
and none is filed before the one ahead of it.  The deed registration is
also filed only after draft A2 (deviations) is ratified.

This registration is number 2.  Its specification, the K9 Component
Contract Specification v1.0.0, is marked Normative.  It is filed after
application/vnd.metadatastician.k9.coordination.

Type name:
  application

Subtype name:
  vnd.metadatastician.k9

Required parameters:
  N/A

Optional parameters:
  security-level
    One of "kennel", "yard", or "hunt" (case-insensitive).
    Indicates the maximum execution privilege the component requests.
    Defaults to "kennel" if absent.  This parameter is advisory; the
    authoritative security level is declared in the pedigree metadata.

  version
    The pedigree.schema_version the component declares.  Syntax:
    major.minor.patch (e.g., "1.0.0").  Advisory, like security-level:
    the value inside the pedigree is authoritative.  This is NOT the
    version of the contract a reader validates against; the
    specification keeps those two numbers separate and forbids
    inferring one from the other.

Encoding considerations:
  8bit

  K9 files are UTF-8 text with no NUL octet.  Line 1 is exactly the
  three octets "K9!" (0x4B 0x39 0x21) followed by LF: no byte-order
  mark, no trailing whitespace, no case variants.  Line endings are LF
  only; a CR+LF file is non-conforming (rule K9-E003), because a CR in
  the magic line would make it four octets and byte-sniffers would
  then disagree with validators.

  No line is longer than 998 octets, not counting the LF that ends it
  (rule K9-E006).  Nickel itself sets no limit; this is a K9 envelope
  rule, so a file with a longer line does not conform and the 8bit
  label is exact.

  After the magic line and an SPDX comment header, the body is a
  single Nickel term.  The magic line itself is NOT Nickel: a reader
  that evaluates the body MUST first replace it with a Nickel comment,
  keeping line numbers stable (the "envelope-strip rule").

Security considerations:
  K9 implements a tiered Leash System with three security levels:

  - Kennel (Pure Data): No execution.  Read-only.  Safe anywhere.
  - Yard (Validation Only): Nickel contract evaluation in a sandboxed
    context.  Nickel is functionally pure -- no side effects, no
    filesystem access, no network access.  Resource limits MUST be
    enforced.
  - Hunt (Full Execution): Complete must-just-nickel triad.  REQUIRES
    Ed25519 signature verification, explicit user consent, and
    containerised execution (Podman-first) where available.

  Unsigned or improperly signed Hunt-level components MUST be rejected.

  Threat mitigations: signature-gated execution, contract isolation,
  bounded Nickel evaluation, replay prevention via timestamped
  signatures, tiered privilege escalation to prevent dependability
  collapse.

  Privacy: pedigree metadata may contain author information and
  deployment targets.  Implementations SHOULD strip metadata before
  sharing across trust boundaries.

  A signature block is a claim, not a verification: a reader MUST NOT
  treat a component as verified because a signature is present.  A
  well-formed component is a well-formed REQUEST for privilege, not an
  authorisation.  See "Security considerations" in the K9 Component
  Contract Specification for the complete list.

  Referenced formats and linked resources: the body is Nickel, and a
  Hunt-level component also names Just recipes and POSIX shell
  scripts, which a host executes only after the Hunt preconditions
  hold.  Pedigree metadata may reference external binary artefacts by
  hash.  A processor MUST NOT fetch or run such an artefact on the
  strength of the reference alone.  The format defines no compression
  and no container format, and no binary payload block.

  Misclassification is a security risk.  The magic "K9!" is shared with
  application/vnd.metadatastician.k9.coordination.  A reader that
  applies the component contract to a coordination file, or the
  reverse, reports wrong results.  Readers MUST classify by the rule
  given under "Magic number(s)" before validating.

Interoperability considerations:
  K9 targets multi-architecture permanence (Linux, Minix, macOS,
  Android, embedded/ASIC at Kennel level).  The must-just-nickel triad
  provides environment detection (POSIX shell), task orchestration
  (Just), and typed validation (Nickel).

  Kennel-level interop requires only magic-byte detection and metadata
  extraction.  Yard requires a Nickel evaluator.  Hunt requires Nickel,
  Just, and Ed25519 verification.

  The format is self-describing via pedigree metadata blocks.  The
  body syntax is Nickel (https://nickel-lang.org), which is normative
  by reference; K9 defines no grammar of its own beyond the envelope.

  Companion type: application/vnd.metadatastician.k9.coordination. The
  k9-coordination dialect (coordination.k9) shares the "K9!" magic but
  has a YAML-like body with its own ABNF grammar, never executes
  anything, and is versioned separately, so it is registered as its own
  subtype rather than as a parameter of this one (owner ruling,
  2026-10-13).  Parameters are routinely dropped by file-type detectors,
  which would label coordination files as Nickel components.  Files
  carrying the magic MUST be classified by their first significant line
  before validation (K9 Component Contract Specification, "K9-E005 - the
  discriminator"); a coordination file is never
  application/vnd.metadatastician.k9 content.

Fragment identifier considerations:
  Dot-separated paths into the component's data structure.

  Syntax:  #<path>  where <path> is key *( "." key ),
           key = 1*( ALPHA / DIGIT / "_" / "-" )

  Examples:
    #pedigree.name       -- component name
    #config.server.port  -- nested config value

  If no key matches, user agent SHOULD treat as unresolvable (no error).

Restrictions on usage:
  None, subject to Leash System enforcement.  Hunt-level files MUST
  NOT be executed without cryptographic verification and user consent.

Additional information:

  Deprecated alias names for this type:  N/A
  Magic number(s):  "K9!" (0x4B 0x39 0x21) at byte offset 0, followed
                    by LF.  A CR before the LF is non-conforming
                    (K9-E003), so for this type the magic line is
                    exactly four octets: 0x4B 0x39 0x21 0x0A.

                    The same three octets begin
                    application/vnd.metadatastician.k9.coordination
                    files, whose magic line may end in
                    LF or CR+LF.  The magic alone does not identify the
                    type.  The rule that tells the two apart is
                    K9-E005 (K9 Component Contract Specification).
                    Read the first significant line after the magic
                    line and the "# SPDX-" comment header:

                      - "{", "[", "(", "let ", a string literal, or an
                        "identifier =" binding: a Nickel term, so
                        application/vnd.metadatastician.k9.
                      - a bare "key:" line (no "="): a coordination
                        file, so
                        application/vnd.metadatastician.k9.coordination.
                      - "---": routed to the coordination type and
                        rejected by its grammar, so it is never
                        application/vnd.metadatastician.k9.
                      - anything else: unclaimed.  It is a defect and
                        is neither type.
  File extension(s):  .k9.ncl  (".k9" is
                       application/vnd.metadatastician.k9.coordination)
