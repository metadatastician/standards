== Status

The K9 Coordination File Specification is *STABLE* at version {version}.

The normative parsing grammar is
link:spec/abnf/coordination-k9-grammar_v1.2.abnf[K9 Coordination ABNF v1.2.0]. If this README or the prose
specification disagrees with the ABNF about syntax, the ABNF wins.

The implementation roadmap is currently at *Phase 1*. The grammar already
supports the optional `coordination:` section used by Phase 2.

== Overview

The K9 Coordination Protocol defines a standard way to express project
invariants, protected paths, architectural decisions, prohibited patterns,
terminology, ecosystem relationships, and mutable coordination state.

A repository stores this operational governance in a single
`coordination.k9` file. A generator reads that file and emits native
instruction files for each supported AI coding tool.

K9 is a *Kennel-level* format: pure data with no execution, functions, or
evaluation.

K9 is YAML-like, but it is *not YAML*. Implementations MUST use a K9-aware
parser conforming to link:spec/abnf/coordination-k9-grammar_v1.2.abnf[coordination-k9-grammar_v1.2.abnf], not a generic YAML
parser.

== The Problem

When multiple AI agents—Claude, Copilot, Cursor, Gemini, Codex, and
others—work on the same codebase sequentially or concurrently, they often
lack shared context about:

* What is intentional rather than accidental
* Which architectural decisions are deliberate
* Which invariants must not be violated
* Which files and directories require approval to modify
* What must not be created
* What another agent is currently working on
* Which terminology is correct for the project

This can lead to well-meaning destruction: agents “fixing” intentional
features, creating parallel systems, replacing deliberate architecture,
or modifying protected files because they lack operational context.

== The Solution

Each repository SHOULD have one `coordination.k9` file at its root. It is
the authoritative source for operational AI coordination and:

* Declares *invariants*—rules agents must not violate
* Protects *paths*—files and directories requiring user approval
* Records *architecture*—decisions that may otherwise look accidental
* Prohibits *creation*—patterns and systems that must not be introduced
* Defines *terminology*—correct and incorrect project terms
* Describes the *ecosystem*—dependencies, consumers, and related projects
* Coordinates *work*—active, completed, and available tasks

When `project.deed_ref` is present, K9 references a DEED file for typed
repository identity. K9 remains the operational source of truth; DEED is
the epistemic identity record.

== File Roles

[cols="1,1,3"]
|===
| File | Requirement | Purpose

| `coordination.k9`
| SHOULD
| Operational governance: invariants, protected paths, architecture,
  prohibited patterns, and coordination state.

| `repo_chora.deed` or `<project>_chora.deed`
| OPTIONAL but RECOMMENDED
| Typed epistemic identity and provenance. Referenced through
  `project.deed_ref`.

| `0-AI-MANIFEST.a2ml`
| Legacy, pending migration
| A2ML is retired (owner rulings D308, D313). Existing copies are legacy;
  never create a new one. Its deed-era home is an
  open owner decision (`1-formats/deed/mappings/ai-manifest-decision.adoc`).
|===

The discovery flow is:

----
coordination.k9            (repository root)
  → project.deed_ref
    → <project>_chora.deed
----

Descriptive state (state, meta, ecosystem, agentic, neurosym, playbook)
lives in clauses of `<project>_chora.deed` (owner ruling D312), not in
separate `.a2ml` files.

== Key Syntax Rules

A conforming `coordination.k9` file follows these rules:

. The first line MUST be exactly `K9!`.
. No whitespace or UTF-8 BOM may precede the magic number.
. One or more `# SPDX-` header lines MUST immediately follow the magic line.
. Syntax is case-sensitive:
  ** `K9!` is valid; `k9!` is invalid.
  ** `metadata:` is valid; `Metadata:` is invalid.
  ** `schema_version:` is valid; `Schema_Version:` is invalid.
. Indentation MUST be exactly two spaces per level.
. Tabs are INVALID.
. Files MUST be valid UTF-8 without a BOM.
. LF and CRLF line endings are accepted. Mixing them is permitted but
  discouraged.
. Blank lines and full-line `#` comments are permitted between sections,
  not within a section. A `---` separator is invalid.
. List items are indented one level deeper than their key, including
  `languages:` items (four spaces under the two-space key).
. Inline comments following a value are not supported.
. Strings use double quotes and support only `\"`, `\\`, `\n`, and `\t`
  escapes.
. K9 does not support YAML anchors, aliases, tags, flow mappings, or other
  general YAML syntax.

== Schema Summary

=== Required sections

Required sections MUST appear exactly once in this order:

. `metadata`
. `project`
. `invariants`

[cols="1,3"]
|===
| Section | Purpose

| `metadata`
| Identifies the K9 schema, schema version, generator, and update date.

| `project`
| Provides operational project information. The required fields are
  `name`, `description`, `license`, and `repo`. The optional `deed_ref`
  field links to typed DEED identity.

| `invariants`
| Defines rules that agents must not violate. The section is required but
  MAY contain zero entries.
|===

An empty invariant section is represented as:

[source,text]
----
invariants:
----

The YAML flow-list form `invariants: []` is not part of K9 syntax.

=== Optional sections

Optional sections MUST appear in this order when present:

. `protected`
. `architecture`
. `do_not_create`
. `terminology`
. `ecosystem`
. `coordination`

Each optional section MAY appear at most once. If present, it MUST contain
at least one entry or subsection.

[cols="1,3"]
|===
| Section | Purpose

| `protected`
| Paths that must not be deleted, reorganised, replaced, or modified
  without explicit user approval.

| `architecture`
| Deliberate architectural decisions and rejected alternatives.

| `do_not_create`
| File patterns or system descriptions that must not be introduced.

| `terminology`
| Correct project terminology and known incorrect alternatives.

| `ecosystem`
| Dependencies, consumers, and related repositories.

| `coordination`
| Mutable active, completed, and available work state.
|===

== Minimal Example

[source,text]
----
K9!
# SPDX-License-Identifier: MPL-2.0

metadata:
  schema: k9-coordination
  schema_version: 1.2.0
  generated_by: k9-init
  last_updated: 2026-04-09

project:
  name: "example-project"
  description: "Example project using K9 coordination"
  license: MPL-2.0
  repo: hyperpolymath/example-project

invariants:
----

If typed DEED identity is available, the project section MAY include:

[source,text]
----
  deed_ref: example-project_chora.deed
----

The referenced file MUST exist and MUST parse as a valid `repo-deed`.

== Usage

Generate all supported instruction files:

[source,shell]
----
deno run --allow-read --allow-write \
  standards/k9-coordination-protocol/generator/generate.js \
  ./coordination.k9
----

Generate selected targets:

[source,shell]
----
deno run --allow-read --allow-write \
  standards/k9-coordination-protocol/generator/generate.js \
  ./coordination.k9 \
  --targets claude,cursor,copilot
----

Before writing output, the generator MUST:

. Parse the entire input using a K9-aware parser.
. Validate the input against the normative ABNF.
. Apply the semantic validation rules from the K9 specification.
. Resolve and validate `project.deed_ref`, if present.
. Stop without changing generated files if validation fails.

A generic YAML parser is not a conforming K9 parser. The conforming
validator is `tools/validate/` (`bun validate.js FILE`); see its README for
what a pass covers.

== Generated Output

Generated files MUST:

. State that they were generated from `coordination.k9`.
. Include a “DO NOT EDIT DIRECTLY” warning.
. Render applicable K9 sections in the target’s native instruction format.
. Preserve attribution between information obtained from K9 and DEED.
. Be generated deterministically.
. Produce byte-identical output when run twice with identical inputs.

Generated files SHOULD be committed so that AI tools receive coordination
context immediately when they start.

If a target file supports custom human-authored content, the generator MUST
either:

* Preserve that content through explicitly marked custom regions; or
* Refuse to overwrite a file it does not own.

It MUST NOT silently destroy unmanaged content.

== Capability Phases

The phases describe protocol adoption and generator behavior. They do not
change the K9 grammar.

=== Phase 1: Defensive — current implementation maturity

The K9 file declares what is and is not negotiable:

* Invariants
* Protected paths
* Architecture decisions
* Prohibited creation patterns
* Terminology

Every supported AI tool receives the same operational constraints. This
phase is intended primarily to prevent accidental destruction.

=== Phase 2: Coordination — syntax available

The optional `coordination:` section records:

* Active agents and work areas
* Start dates and status
* Blockers
* Completed work
* Available work

The grammar already supports this section. A deployment reaches Phase 2
when agents and tooling reliably read and update the coordination state
without modifying stable human-authored sections.

=== Phase 3: Orchestration — planned behavior

Agents report completion, discover available work, identify follow-on
tasks, and flag integration points between parallel efforts.

Phase 3 is an implementation roadmap. It does not currently define
additional K9 syntax. New fields or sections require a specification and
grammar revision before use.

== Relationship to DEED

K9 and DEED are complementary:

[cols="1,2,2"]
|===
| Concern | K9 | DEED

| Primary role
| Operational governance
| Typed epistemic identity

| Typical mutability
| Stable except for `coordination:`
| Immutable and versioned

| Syntax
| Strict YAML-like K9 syntax
| S-expressions

| Connection
| `project.deed_ref`
| Referenced `repo-deed`
|===

If `deed_ref` is present:

* The referenced file MUST exist.
* It MUST parse as a valid `repo-deed`.
* Its filename and document head MUST satisfy DEED dispatch rules.
* Its `:canonical-name` SHOULD match `project.name`.
* A mismatch SHOULD produce a warning.
* DEED remains authoritative for typed identity.
