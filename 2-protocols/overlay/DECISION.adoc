= Overlay Protocol — Keep-Spec Decision
Jonathan D.A. Jewell <j.d.a.jewell@open.ac.uk>
:updated: 2026-04-05
:decision: KEEP-SPEC-DEFER-IMPL

== Decision

**Keep the spec. Defer implementation.**

The overlay-protocol directory contains a specification
(`OVERLAY-PROTOCOL-SPEC.adoc`, 429 lines), an Idris2 ABI skeleton
(`src/abi/OverlayProtocol.idr`), a Zig FFI implementation (`ffi/zig/`),
and a shell conformance checker (`scripts/check-conformance.sh`). There
is no consumer, and no CI lane builds or runs the Zig code or the shell
checker.

[NOTE]
====
Corrected 2026-11-17. The 2026-04-05 text called the Zig FFI "an empty
scaffold" and said there were no tests. Both were wrong: see
<<whats-there>>. The decision itself is unchanged.
====

Three options were considered:

[cols="1,3,2",options="header"]
|===
| Option | Pros | Cons

| Complete
| Spec gets a validated implementation: the Zig runtime built and tested
  in CI, a pinned Zig version, and a correspondence argument to the model
| No consumer yet — risk of building to no requirements; significant work
  while other protocols (AVOW, Groove) have active consumers

| Archive
| Reduces standards-repo noise; removes dead code paths
| Loses the spec (420 lines of thinking); the topic may become relevant
  and reintroducing it later is costly

| **Keep spec, defer impl** (chosen)
| Spec remains discoverable and citable; zero maintenance cost until a
  real consumer appears; the ABI skeleton and the unvalidated Zig FFI
  document the intended shape
| Standards repo lists a protocol with no validated runtime (the Zig code is
  neither built nor tested in CI) — must mark clearly
|===

== What the Zig FFI contains (checked 2026-11-17)

`ffi/zig/` is not empty:

* `src/main.zig`, 575 lines. It defines `PeerType`, `Result`,
  `ConformanceFlags`, `OverlayDeclaration` and `BaseState`, and exports 16
  C-ABI functions (`overlay_declaration_new`, `overlay_declaration_set_field`,
  `overlay_check_non_modification`, `overlay_check_additive`,
  `overlay_check_switchable`, `overlay_check_idempotent`,
  `overlay_check_declaration`, `overlay_check_conformance`,
  `overlay_is_conformant`, `overlay_pass_count`, `overlay_check_composable`,
  `overlay_check_mixed_composable`, `overlay_peer_type_name`,
  `overlay_peer_types_distinct`, `overlay_last_error`, `overlay_version`).
  They are runtime checks over caller-supplied states at one base state.
  `VERSION` is `1.0.0-draft`.
* `src/main.zig` also holds 17 `test` blocks (invariant pass and fail
  cases, peer type names, the last-error buffer, version).
* `test/integration_test.zig`, 189 lines, 7 scenario tests (conformant
  o-extension and aggregate-library overlays, a base-modifying overlay, a
  non-reversible activation, mixed and same peer types, a declaration
  missing `upstream_url`).
* `build.zig`, 68 lines. It builds a shared and a static library and has
  `test` and `test-integration` steps.

What is not established:

* The 24 Zig tests were written but not run for this correction. `zig` is
  not installed here and `ziglang.org` returns 403 through this session's
  proxy, so they give no `tested-only` evidence.
* No Zig version is pinned. There is no `build.zig.zon`, no
  `.tool-versions`, and no Zig in `guix.scm`.
* No CI lane builds or tests the Zig code or runs `check-conformance.sh`;
  the one workflow that mentions the overlay, `echidna-verify.yml`,
  deliberately excludes the Idris2 file.
* No correspondence argument ties the Zig code to the Idris2 model.

. Spec section 4.3 aggregate-library
. Spec section 7.1 conformance checklist items no other row covers
. Spec section 6 composition and chaining

Two Idris2 facts are `proven` (`peerTypeExhaustive`, `peerTypesDistinct`),
relative to an `argued` row for the Idris2 library they import.

== Actions taken

1. This document records the decision
2. The spec remains at `OVERLAY-PROTOCOL-SPEC.adoc` (unchanged)
3. README and ROADMAP will mark overlay-protocol as `SPEC-ONLY` status
4. TOPOLOGY / PROTOCOLS listings should include the `SPEC-ONLY` tag
5. CRG grade for overlay-protocol: **E** (exploratory — spec exists, no
   field validation)

== When to revisit

Revisit this decision if ANY of these become true:

- A concrete consumer emerges that needs overlay-protocol semantics
- AVOW, Groove, or another adjacent protocol wants to delegate to overlay
- The spec itself becomes a citation target outside hyperpolymath

Until then, no effort is spent on overlay-protocol.

== Rationale for NOT archiving

The spec describes a class of problems (protocol overlays on existing
transports) that will recur. Keeping 420 lines of careful design thinking
costs nothing and preserves optionality. Archiving would mean rediscovering
the same design space later.
