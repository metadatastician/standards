This is the ownership record for the shared governance source in
`metadatastician/standards` and the handoff to its consumers. It states exactly
what was repaired, what was **not** (there is no duplicate lock-record fix), the
published source, the verification that was run, and what a consumer must do —
with the one trap that makes a naive repin dangerous.

== 1. Published source

The commit is immutable in the ordinary sense: it is a content-addressed object
on a pushed branch, anyone can `git fetch origin <sha>` and reproduce every
result below. It is **not** the merge target, and that distinction matters:

IMPORTANT: this repository's ruleset allows **squash and rebase** merges only,
and requires signed commits. Both merge methods *rewrite* the commits in this
branch. So the SHA above will **not** be an ancestor of `main` after merge — a
squash merge deletes it from history outright. **Do not pin a consumer to it.**
Consumers pin the **merge commit on `main`**, after re-running the canary there
(section 6, step 2). The SHA above is the evidence that the repair is real, not
the thing to consume.

Why it is not merged: this environment has no signing key, and the ruleset
requires signed commits plus code-owner review. `--admin` bypass was not used
and will not be — the requirement is the point.

=== What is still not proven, and why

`governance-reusable.yml` is exercised here by a **local** call
(`./.github/workflows/governance-reusable.yml`), so `job.workflow_sha` resolved
to the *calling commit*. A consumer calls it **remotely** at a pinned SHA, where
the same expression resolves to *that* SHA. The remote-resolution mechanism
itself is exercised in this repository today — `ci-pipeline.yml` calls
`secret-scanner-reusable.yml@d55304a0` remotely and it ran 3 jobs with 10/3/3
steps at the published SHA — but the *governance* reusable has not yet been
called remotely at this SHA by anyone.

That is deliberate: proving it means a consumer repin, and the ordering matters
(publish → test → repin). It is section 6, step 2, and it is the gate the user's
brief calls for. **Do not treat this document, or a green canary, as that
proof.**

== 6. Consumer migration

Two classes of consumer. The first *must* act; the second may.

. **Startup-dead pins — repin required.** `svalinn` (`fad242d3`),
  `odraz` (`da2c748a`), `cadastra` (`e3b9929c`), `lintel` (`e16a2317`). Each
  pin's own `lock-selfcheck` verdict is POISON (51 / 56 / 36 / 6 self-SHA
  records; `cadastra` also has 1 dangling edge), and each has a governance run
  with zero jobs or one-step jobs. Repin to the merge commit of this PR.
. **Healthy pins — optional.** `burble`, `marid` (`01c9b0c9`) and `main` itself
  are SELF-CONSISTENT and run policy. They gain the third-pin and float
  repairs, not a fix for an outage. Repin on the normal cadence.

Steps, in order:

. **Merge** this PR (a signed, linear merge — the ruleset's, not a bypass).
. **Test the exact commit you will pin**, not the branch:
+

[source,bash]
----
git fetch origin main && git checkout --detach origin/main
bash scripts/tests/governance-canary-test.sh "$(git rev-parse HEAD)"
bash scripts/check-reusable-closure.sh .github/workflows --repo metadatastician/standards
bash scripts/lock-selfcheck.sh "$(git rev-parse HEAD)"
----

+
A red canary means **do not repin** — read the named finding, fix the source,
repeat. `governance-canary-test.sh <sha>` extracts that commit with
`git archive` and tests *it*, so the result belongs to the SHA you pass.
. **Repin the consumer's `uses:` to the 40-hex merge commit** (`@<sha>`); a tag
  or branch re-creates the class this repair removes.
. **Repair the consumer's own lock in the same PR.** This is not optional and it
  is the part the fleet has been getting wrong: `svalinn` carried the poisoned
  record **in its own `.github/workflows/actions.lock`** at the failing run, so a
  corrected callee alone would not have saved it. Run the pipeline:

[source,bash]
----
gh actions-lock --no-migrate-local-actions --no-narrow
scripts/relock-sha-keys.sh && scripts/complete-job-refs.sh && scripts/close-lock.sh
scripts/prune-stale.sh                      # consults the closure baseline
scripts/check-lock-pin-contract.sh && scripts/check-lock-sync.sh
----

. **Probe the remote path before trusting it** (this is the evidence that does
  not yet exist for `governance-reusable.yml` at a consumer). One job, its own
  workflow, `workflow_dispatch` only, calling the reusable at the pinned SHA
  with the policy that matters least. Success = a job with more than one step.
  One step = still dead; read the annotation, do not merge the repin.
. **Re-measure and record**: the governance run URL, the job count, and the step
  count of `Language / package anti-pattern policy`. One step per job is a
  startup failure wearing a green check's clothes — it is not a policy result.
. **Keep the required checks.** Do not add `continue-on-error`, do not demote a
  gate to `::warning::`, do not widen `allowed-actions` to make a repin pass, and
  do not take an admin bypass. If a gate fails after the repin, it is finding
  something real; that is the repair working.

Consumers passing `canon-ref:` (fork-governance) or `standards-ref:`
(readme-derive) with a **branch** must change to a 40-hex commit or delete the
input — the new defaults do not float.

|one site here
|third-pin sites: restore `ref: 317101e03b8f…` (and accept that

indistinguishable from no guard.
|===

== 8. Coordination, and what is blocked

* **Hypatia (source ownership).** The shared source owns the workflow; Hypatia
  owns the baseline contract. Two asks: (a) confirm that
  `validate-hypatia-baseline` + `.machine_readable/hypatia-baseline.schema.json`
  in this repository is the current contract, so the gitbot-fleet patch can be
  retired rather than rebased; (b) note that PI006 (self-SHA record) and
  `invalid_actions_lock` already agree with the guards here — no rule change is
  requested, and none is offered.
* **cyo (downstream adoption).** The migration list is section 6. The two asks
  that need an owner: sequence the four startup-dead repins so the probe run
  (step 5) happens on one repository first, and hold every other consumer at its
  current pin until that probe is green. A wave of simultaneous repins converts
  four known-dead callers into an unknown number of differently-dead ones.
* **gitbot-fleet (automation).** The lock-sync automation must run the pipeline,
  never `gh actions-lock` alone (it cannot emit job-level or through edges), and
  must never "fix" a failing guard by editing the guard. The stale patch above is
  the concrete example of the failure mode to avoid.
* **Blockers.** (1) The merge itself: no signing key in this environment, and
  the ruleset requires signed commits + code-owner review — so the published SHA
  is a branch commit and the merge must be done by an owner, not bypassed.
  (2) Issue-comment API returns **403** for this token, so the cross-links to
  #968/#1290 live as PR comments; they need reposting by an actor with issue
  write access. (3) `gawk` is a hard precondition of `prune-stale.sh`; on a
  `mawk` host it exits 1 without touching the lock, which a wrapper that ignores
  the exit code reads as "nothing was stale".

   justification is a measurement (#968), not convenience.
