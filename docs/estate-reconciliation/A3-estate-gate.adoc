Specification A3 of the Estate Reconciliation Plan. It defines the one required status check of a repo, the one caller workflow, the table from profile to checks, and the rules by which a verdict is computed.

== 1. Summary

* A repo has exactly 1 required status context. Its name is `estate-gate`, and it is a commit status context. Any publisher may post it [O].
* A repo has exactly 1 caller workflow, which calls a reusable aggregate at a full SHA. The caller has no per-repo inputs. The profile comes from the repo chora (A2).
* The set of required checks is: baseline, plus the checks of declared capabilities, plus the checks of capabilities detected in the tree [O]. A repo cannot dodge a check by under-declaring.
* A required check that did not run fails the gate. Owned-compute checks get a bounded wait, then fail [O]. There is no pass on absence.
* The check table is a new table in `proven-cicd`, keyed by A2 capability names [O]. It replaces the per-profile file detection in `gates.json` as the source of required checks.
* A name-only context cannot be bound to a publisher. A3 therefore requires a signed verdict envelope and a post-merge verification of every merged head (section 9).
* A3 does not widen the required set. Its first table reproduces the checks that are required today (section 5.3). Widening needs an owner ruling.

== 3. The gate

=== 3.1 Name and kind

* The required context is `estate-gate`. It is a commit status context [O].
* No component, input or advisory result is ever a required context. Their names are listed as never required (section 11).
* The ruleset for a repo requires `estate-gate` and no other status context. It sets no `integration_id`, because a commit status is not published by the Actions integration [I].

=== 3.2 Publishers

Any of these may post `estate-gate` on a head commit:

[cols="1,3"]
|===
| Publisher | When

| Actions aggregate | The default. The caller's job runs the reusable aggregate, which posts the status with the job's `GITHUB_TOKEN` (`statuses: write`).
| Owned compute | When Actions is unavailable or its minutes are exhausted. The farm or the mesh runs the same aggregate code and posts the status. [R: plan, R1; `continuation-mesh` bridge [M]]
| `workflow_run` publisher | For a pull request from a fork, whose token is read-only (section 2, finding 11).
|===

All publishers run the same aggregate, from the same pinned source, and compute the same verdict function (section 7). The status carries `target_url` pointing to the verdict envelope (section 3.4). A publisher that is not the Actions aggregate MUST post only after it has verified every owned-compute input.

=== 3.3 Status states

[cols="1,3"]
|===
| State | Meaning

| `pending` | The aggregate has started, or is within the bounded wait for an owned-compute input.
| `success` | Verdict `pass` (section 7).
| `failure` | Verdict `fail`. The description names every failing check.
| `error` | The aggregate itself could not compute a verdict (chora unreadable, table unreadable). Never `success`.
|===

The description is at most 140 characters and names the first failing checks and a count [I: GitHub's status description limit]. The full list is in the envelope.

=== 3.4 Verdict envelope

The `target_url` resolves to an envelope with at least: the head SHA; the pin of the aggregate and of the check table (commit SHA and sha256); the repo chora blob SHA; the required set with the state of each check; the findings each check reports, warnings included; the waivers applied; the publisher id; the time; and a signature (section 9). The storage location and the format are for A4, which owns the intake envelope [R: plan A4]. A3 fixes the fields. A4 section 5 fixes the encoding and the storage (decision E9 is resolved there).

== 4. The caller contract

=== 4.1 The file

Each repo carries exactly one caller: `.github/workflows/estate-gate.yml`, job id `gate`, and one fork publisher (4.4). The job ids and the file names are frozen, like every context-producing name (finding 3).

----
name: Estate gate
on:
  pull_request:
    branches: ["<default-branch>"]
  merge_group:
  push:
    branches: ["<default-branch>"]
  workflow_run:
    workflows: ["Governance", "Hypatia Security Scan", "Secret Scanner"]
    types: [completed]
concurrency:
  group: estate-gate-${{ github.event.workflow_run.head_sha || github.event.pull_request.head.sha || github.sha }}
  cancel-in-progress: false
permissions:
  contents: read
  checks: read
  actions: read
  statuses: write
  id-token: write
jobs:
  gate:
    uses: hyperpolymath/proven-cicd/.github/workflows/estate-gate.yml@<40-hex commit>
----

The generator fills `<default-branch>` with the repo's default branch, for example `main` or `master` (rule 1 of 4.2). The sample parses as YAML once the two placeholders are filled [M]. I did not run it on GitHub [I].

=== 4.2 Rules

. The caller has no `with:` inputs and no `secrets:` other than what the reusable names. All per-repo facts come from the repo chora. The template has 2 generated values: the 40-hex pin and `<default-branch>`, which the generator takes from the repo's default branch on the platform. A caller that differs from the template in anything else is a deviation of kind `exemption` for rule `generation/drift`, or it is drift.
. The reference is `<owner>/<repo>/.github/workflows/estate-gate.yml@<full 40-hex SHA>`. A branch or tag reference is invalid, because it startup-fails under `sha_pinning_required` [M: audit header]. The caller is de-onboarded from `actions.lock`, as the existing audit caller is.
. The triggers include `pull_request` on the default branch, and no `paths` or `paths-ignore` filter. A path-filtered caller does not run on every PR, so `estate-gate` would never report on some heads and the PR would wait forever (finding 5).
. `merge_group` is present so that a merge queue can satisfy the gate [I].
. `workflow_run` (`completed`) of the three inline workflows, named as the template names them ("Governance", "Hypatia Security Scan", "Secret Scanner"), is present so that a re-run of an inline job recomputes the gate (5.3).
. `concurrency` groups the caller's runs by head commit, with `cancel-in-progress: false`: the head SHA of the `workflow_run`, else of the pull request, else `github.sha` (for `push` and `merge_group`). Runs for one head therefore publish one at a time, and GitHub keeps only the newest waiting run, which reads its inputs after the run before it has posted. Without it, two recomputations can overlap and the older one can post last (5.3).
. `permissions` is `contents: read`, `checks: read`, `actions: read`, `statuses: write` and `id-token: write`. `checks: read` and `actions: read` let the aggregate read the inline-job inputs of 5.3 (Q6): the check runs, and the workflow runs that name their files. `id-token: write` lets the reusable aggregate request the OIDC token for the attestation of section 9.1 (A4 F3). A called reusable workflow cannot raise the permissions of its caller, so the caller must grant it [I: GitHub reusable-workflow permission rules]. No other permission is granted to the caller.
. The pin is advanced by a reviewed PR. The existing weekly tracker `track-estate-audit.yml` does this for the audit [M]. A3 does not define a new tracker.
. The caller is a generated file. A2's `(generation)` records the pack that produced it. Law L4 (A2) applies: realign may overwrite it, because it is an `engine` file.

=== 4.3 Suite coordinate

The coordinate `hyperpolymath/proven-cicd` is the canonical one [M: README]. The other 2 names in estate documents are historical (finding 8). Decision E2.

=== 4.4 Fork publisher (E8)

A pull request from a fork runs the caller with a read-only token, so the aggregate cannot post `estate-gate` there (finding 11). The repo therefore also carries `.github/workflows/estate-gate-publish.yml`, job id `publish`, generated from the same pack as the caller, on the pattern of `fork-governance-publish-reusable.yml` [M]:

----
name: Estate gate publish
on:
  workflow_run:
    workflows: ["Estate gate"]
    types: [completed]
permissions:
  actions: read
  statuses: write
jobs:
  publish:
    uses: hyperpolymath/proven-cicd/.github/workflows/estate-gate-publish.yml@<40-hex commit>
----

. In a fork run the aggregate computes the verdict and uploads the verdict envelope (3.4) as an artifact. It posts nothing.
. The publisher runs from the default branch, with the base repo's token. It downloads the artifact of the triggering run and accepts it only when the run's head SHA equals the envelope's subject commit and the envelope is valid (9.1). It then posts `estate-gate` on that head SHA. It never checks out or runs code from the fork.
. An artifact that is missing or invalid gives `estate-gate` `failure` with the reason, never no status (law G3).
. The publisher's rules match 4.2 rules 1, 2 and 6: no `with:`, a full-SHA pin, pin advanced by a reviewed PR.

== 5. The check table

=== 5.1 Form

The table is a `praxis-deed` named `estate-gate_praxis.deed` that `proven-cicd` owns, with a `(checks)` clause profile. It reuses the head that A2 chose for packs. It needs no grammar change.

----
(praxis-deed
  :schema-version "1.0.0"
  :canonical-name "estate-gate"
  :beholding-chora #uuid"0889b37b-defb-831f-973c-e119500db00e"
  (checks
    (check :id "secret-scan" :when baseline :obligation required
           :runs-on github :rule "check/secret-scan")
    (check :id "rust-ci" :when rust :obligation required
           :runs-on either :timeout 900
           :detect ("Cargo.toml" "*/Cargo.toml") :rule "check/rust-ci"))
  (contractiles-adopted
    (repo :chora #uuid"806d4d6f-f107-8b36-939b-f89ba6279377" :from "2026-12-01")))
----

The `(contractiles-adopted ...)` clause lists every repo that adopts the `(contractiles ...)` clause (A7 8.4, YC10). An entry is `(repo :chora #uuid"..." :from "YYYY-MM-DD")`: the repo's opaque chora id and the date from which it is held to the clause. The entry lives in this table's repo, so the adopting repo's own PR cannot add it (one repo per PR, A7 YR04). The table PR comes first and sets `:from`; the repo's PR then adds the clause before that date. For `standards` that PR is M4; for a migrated repo, M7. A repo born from the template with the clause is listed at registration, with `:from` its registration date. The list is append-only: an entry is never removed, and a change to the table that removes one fails its own check (test G64). An entry's `:from` cannot move later, is a valid `YYYY-MM-DD` date (as A2 V06), and each chora id has exactly one entry, which must resolve to a registered repo chora in chora-registry. A listed repo must also pin the aggregate and this table at or after the commit that last added or changed its entry: an older pin would let it read a table without its entry, or with a later `:from`, so it fails (test G65). The list is a pinned input of the verdict, like the rest of the table, and the verdict compares `:from` with the date it already takes as an input (section 7).


The sample in `docs/estate-reconciliation/examples/a3-estate-gate_praxis.deed.example` (the caller sample is `docs/estate-reconciliation/examples/a3-estate-gate.yml.example`) lints clean under `deed_lint.js` as written: `deed.abnf` v1.3.0 and its linter accept the opaque literal since #1473 [M: linted 2026-11-12]. The linter checks syntax only [I].

[cols="2,1,4"]
|===
| Field | Cardinality | Rule

| `:id` | 1, STRING | A `proven-cicd` capability id. Unique with `:when` in the table.
| `:when` | 1, symbol | `baseline`, or an A2 capability name (a root term of kind `capability`).
| `:obligation` | 1, symbol | `required` or `advisory`. An advisory check never fails the gate and never counts toward a required obligation [M: same rule in the mother contract].
| `:runs-on` | 1, symbol | `github`, `owned` or `either`.
| `:timeout` | 0..1, INTEGER | Seconds an input may take: an owned-compute input (section 8), or an inline-job input (5.3). Applies when `:runs-on` is `owned` or `either`, and on the three inline-job rows. When such a row omits it, the default of 5.4 applies. Any other row with `:runs-on github` has none.
| `:detect` | 0..1, list of STRING | Repo-relative globs. A non-empty match means the capability is detected (section 6). A row with `:when baseline` has none.
| `:rule` | 1, STRING | `check/<id>`. The rule identifier that a deviation names (section 10).
|===

A check row appears once per `(:id, :when)`. Where 2 capabilities need the same check, there are 2 rows.

=== 5.2 Where it lives, and what it replaces

The table lives in `proven-cicd`, with the checks it names [O]. It replaces the per-profile detection of `gates.json` as the source of required checks. The ruleset applier then derives its single context from this table and not from emitted job names. The experimental mother profiles (`profiles/mothers.json`) stay experimental and are not used by A3.

*Inline-job contract (Q6 [O], 2026-11-14).* The checks of `governance`, `hypatia-scan` and `secret-scan` live in two places: the template's inline jobs, and the deprecated `standards` reusables, which stay for the callers that already pin them. A3 builds on neither reusable. The aggregate reads each inline job as an input, in the way section 8 reads an owned-compute input:

. The input is the check run that the job emitted on the head commit. It counts only if the GitHub Actions app (integration 15368) created it, its name equals the job name in the row's note, and its workflow run's file path equals the path named there. A check run with another name, app, path or head SHA is not the input.
. The workflow file is bound to its generated content. At the head commit, the file named in the row's note must be byte-equal to the file that the repo's pinned pack generates for it (A2 `(generation)`, as for the caller in 4.2). A pull request can otherwise change the file, keep its path and job name, and replace the check with a step that always succeeds. When the file differs, the check is `failed` with reason `inline-workflow-drift`, whatever the run's conclusion. The pin the comparison uses must itself be trusted, or a PR could move the pin and the file together: it is the pin on the base commit, or, when the PR moves it, a released commit of the canon pack (the same rule as the caller pin, G65). Any other pin gives `failed` with reason `inline-pin-untrusted`. A template update reaches the repo through a realign PR that moves the pin to a release and the generated file with it.
. The inline workflows run on every event the caller runs on (4.2): `pull_request` and `push` on the default branch, and `merge_group`, with no `paths` or `paths-ignore` filter. Otherwise a merge queue head has no input, and G2 fails. The generated files satisfy this; the drift rule above keeps it so.
. One run decides. When several check runs match, for example after a re-run, the one from the most recent attempt of the most recently created workflow run counts. An older attempt never overrides a newer one, so a failure followed by a successful re-run gives `passed`, and a success followed by a failed re-run gives `failed`. A re-run does not start the caller by itself, so the caller also runs on `workflow_run` (`completed`) of the three inline workflows (4.2). Each completion recomputes the verdict for that head and posts it, and the latest post replaces the earlier `estate-gate` status. The latest post must also be the newest computation. The caller's `concurrency` group (4.2) runs one recomputation per head at a time. Immediately before it posts, the aggregate reads the latest attempt of each inline input again. If any differs from the attempt it computed from, it recomputes instead of posting, until the inputs hold still or the row's `:timeout` passes. A status computed from an older attempt is never posted over one computed from a newer attempt.
. While the input has not completed and the row's `:timeout` has not passed, the check is `pending`. After the timeout it is `not_run` and the gate fails. The three inline-job rows carry `:timeout`, although their `:runs-on` is `github`; it defaults to 900 seconds (5.4, E7 as amended on 2026-11-14).
. A conclusion of `success` gives `passed`. `failure`, `cancelled`, `timed_out` and `action_required` give `failed`. `skipped`, `neutral` and `stale` give `not_run`, because a job that skipped or never finished has not checked anything. A check with several jobs, such as `secret-scan`, is `passed` only when every one of its jobs is.
. Reading these inputs needs `checks: read` and `actions: read` in the caller (4.2): the first for the check runs, the second for the workflow run that names the file. `contents: read` covers the file comparison.
. The findings the job reports are copied into the envelope (3.4). The contract names only the inline jobs. A repo that still calls a deprecated reusable takes the template's inline form as part of its cutover (section 11), before the gate is required there.

The `contractiles` row is the one deliberate widening (E12, an owner ruling of 2026-11-13). It fails on a `Must` violation, on a violated clause marked `!`, on a Bust finding graded `X1`, and on a blocking unresolved verdict (A7 8.4). An open anchor no longer fails it: A7 S1 withdrew W6, the open-anchor course correction (A7 v0.2.8). A violation the verb grades as a warning is reported in the verdict envelope (3.4) and does not fail it. Until a repo carries the `(contractiles ...)` clause, or its `contractiles-adopted` entry's `:from` date passes (5.1), the probe finds no subject and the row is `not_applicable`, with that reason in the envelope. From `:from` on, A7 YC01 applies, and deleting the clause does not make the row `not_applicable` again.

All other catalogue capabilities are `advisory` in the first table. Promoting one to `required` is an owner ruling and a table change. The enforcing checks of the original audit (14 of its 26 actions [M: README]) are not required by `gates.json` today (finding 7) and A3 does not require them.

=== 5.4 Defaults

== 6. Applicability

Let `D` be the capabilities that the repo declares in its `(profile)` after resolution (A2 5.2), and `S` the capabilities detected in the tree by the table's `:detect` globs [O].

----
capabilities(repo) = D union S
required(repo) = { c in table : c.obligation = required and (c.when = baseline or c.when in capabilities(repo)) }
----

* A capability in `S` and not in `D` is reported as profile drift (A2 vestigial and missing verdicts). The gate still requires its checks.
* A capability in `D` and not in `S` still requires its checks. A check with no subject is `not_applicable` only when the aggregate's own probe finds no subject. For `contractiles`, no subject means the repo has no `(contractiles ...)` clause and is not held to it: its chora id is not in the table's `contractiles-adopted` list, or its entry's `:from` is after the verdict's date (5.1, E12). A repo that carries the clause is checked whether listed or not. A listed repo whose `:from` has passed has a subject whatever the clause's state, and fails if the clause is missing (A7 YC01, YC10). A check cannot declare itself not applicable.
* Detection is done by the aggregate from the tree at the head commit. It is never read from a deed field (the self-assertion rule [M: deed spec]).
* A detected capability that is not a root term does not enter `S`. The aggregate reports it and does not fail on it (E3 covers adding the terms).

== 7. The verdict function

Each required check ends in exactly one state:

[cols="1,3"]
|===
| State | Meaning

| `passed` | The check ran and exited 0.
| `failed` | The check ran and exited 1.
| `not_run` | The check exited 2 ("no check was performed"), timed out, or its input never arrived.
| `not_applicable` | The aggregate's probe found no subject (section 6).
| `waived` | A valid deviation covers it (section 10).
|===

----
verdict(repo, head) = pass   iff every c in required(repo) is in { passed, not_applicable, waived }
                      fail   otherwise
----

* `not_run` fails the gate [O]. The description names the check and the reason.
* An advisory check has no effect on the verdict. Its state appears in the envelope.
* The function depends only on: the table at its pin, the repo chora at the head, the tree at the head, the check results for the head, the deviations at the head, and the date. Two publishers given the same inputs compute the same verdict (law G1, section 12).
* The aggregate runs every required check to completion even after a failure, so one run names every failing check [M: the same discipline as `main-estate-audit`].

== 8. Owned-compute inputs

R1 allows estate scans on owned compute, through the farm and `continuation-mesh` [O: R1]. A check whose row has `:runs-on owned` or `either` can arrive that way.

. The node posts a commit status on the head commit with context `estate-input/<id>`, state `success` or `failure`, and `target_url` to the signed baton envelope. These contexts are never required.
. The aggregate looks for the input. While none has arrived and the row's `:timeout` has not passed, the check is `pending` and the gate status is `pending`.
. After the timeout the check is `not_run` and the gate fails [O]. A late input that arrives after the gate failed does not change that status. A re-run of the aggregate on the same head may pick it up.
. An input counts only if its envelope verifies (section 9.1) and the signed `check` of its `check-verdict` predicate (A4 5.5) equals `<id>`. An input with no envelope, a bad signature, a check id that differs or a head SHA that differs is `not_run`. The status context alone never binds an envelope to a check.
. `either` means the check may run on GitHub or on owned compute. A result from GitHub and one from owned compute for one head are both read. If they disagree, `failed` wins.

The routing of a check to a node (capability matching) is the mesh's concern [M: `docs/ci-check-baton.adoc`]. A3 states only the input contract.

== 9. Trust: a name-only context cannot be bound

A status context is matched by name. A ruleset cannot bind it to a publisher (finding 4; `integration_id` omitted [I]). Any token with status-write on the repo can post `success` for `estate-gate`. A3 cannot prevent this. It makes it detectable.

=== 9.1 What is verified

* Each owned-compute input carries an ed25519 signature over the canonical string of the baton, with the signing public key. The aggregate accepts the input only when the public key is in the publisher list (9.2). The baton's HMAC digest is keyed by a secret that a GitHub runner does not hold, so the aggregate cannot check it [I]. It is a node-internal integrity check.
* The aggregate signs the verdict envelope (3.4). The signing key is the publisher's. For the Actions aggregate, A4 section 12 (F3) fixes the signing: an OIDC-bound attestation. Until that is in place, the Actions aggregate posts the envelope unsigned and the post-merge check (9.3) treats it as `unsigned`.

=== 9.2 Publisher list

A list of publisher ids and ed25519 public keys is part of the estate's trusted baseline, outside any candidate change. A3 proposes `(publishers (publisher :id "<id>" :ed25519 "<64 hex>"))` in the federation root (E1). A4 F3 adds an OIDC form to an entry. A public key in a public deed is not a secret [I]. The `:id` is a name, and a rotation adds a second entry before it removes the first.

=== 9.3 Post-merge verification

An observer verifies every head that merged. For a merged head it recomputes the verdict from the envelope's recorded inputs and compares it with the posted status. A mismatch, an unsigned envelope from a non-Actions creator, a status creator not in the publisher list, or a missing envelope is reported as `forged-or-unverified`. This is the same design as the deed spec's rule that a judgement is computed by an external observer from observed state. The observer belongs to A4 and to `cadastra`. A3 defines its test (G10).

[IMPORTANT]
====
Detection after merge is weaker than a bound context. A forged `success` merges before anyone looks. The estate accepted this trade by choosing a publisher-independent name [O]. If the estate later wants prevention, the ruleset can add a second required context that only the Actions integration can publish. That is a ruleset change and not a change to this specification.
====

== 10. Deviations and waivers (A2)

. A required check is waived by a deviation (A2 section 7) whose `:rule` is `check/<id>`. The deviation may sit at the repo, estate or root level. A2 7.4 applies: a repo-level deviation may not name a rule that a higher level declares.
. A waiver is valid when: `:authority` is present and names a ruling or issue that the trusted baseline records, outside the candidate change (the base commit of the PR, or the federation root's ruling register, not the head) [I: A5 names the store]; a deviation in the head cannot supply its own authority; `:evidence` is present; `:kind` is `exemption` and its `:review-by` or `:expires` has not passed, or `:kind` is `deferral` and its `:expires` has not passed. A `debt` deviation cannot waive a check, because a check has no measured integer in A3. A5 may add that.
. A lapsed deviation is not valid. The check reverts to its real state, and the gate fails if that is `failed` or `not_run`.
. The envelope lists every waiver that the gate applied. A deviation that names a check that is not required is reported and has no effect.
. The rule identifier namespace `check/` is reserved for A3. Rule identifiers in general are defined by A5 (sections 3 and 4): `check/<id>` is the `check` domain there.

== 11. Cutover rules (A3 performs nothing)

. `estate-gate` is added to a repo's ruleset only after it has reported once on that repo's default branch (the context-witness rule [M]). A ruleset that requires a name nothing has published is a phantom.
. During the transition the old required contexts stay until `estate-gate` is witnessed. The old names are then removed, and they are added to `never_required_contexts` so that the applier cannot re-derive them.
. After the cutover the only required status context of a repo is `estate-gate`. A required list with any other entry is a ruleset defect. The one exception is a context that an app owns and that the owner has ruled to keep (the design spec's bypass and context rulings [R]). Such a context is listed by name in the applier's kept-context list, next to `never_required_contexts`. A context in neither list is obsolete and is removed.
. A repo that cannot satisfy `estate-gate` is reported `UNSATISFIABLE` with the failing check, and is never fixed by a bypass. Doctrine 5 forbids the bypass [R: plan P4].
. A caller that has been generated from a chora whose `(generation)` is absent is `unstamped` (A2 section 8).
. GitHub starts a `workflow_run` listener only once its workflow file is on the default branch, so on the PR that adds the caller a re-run of an inline job does not recompute `estate-gate`. That status can be stale only on this PR, and it cannot make the PR mergeable: by the first rule `estate-gate` is not yet required there, and by the second the old required contexts still gate it. After the last re-run of an inline job on that PR, the author re-runs the caller, whose run reads the latest attempts; a merge queue recomputes again on `merge_group`. The first `push` run on the default branch, which witnesses `estate-gate`, reads its own head's inputs and is not stale.
. A repo whose governance, Hypatia scan or secret scan still runs through a deprecated `standards` reusable takes the template's inline jobs (5.3, Q6) in the PR that adds its caller. Until then those inputs are absent, the checks are `not_run`, and `estate-gate` cannot be witnessed green, so the first rule keeps it from being required there.

== 12. Laws

[cols="1,4"]
|===
| Law | Statement

| G1 | Determinism. The verdict depends only on the inputs in section 7. Two publishers with equal inputs post equal verdicts.
| G2 | Satisfiability. For every repo whose caller satisfies the rules of 4.2, `estate-gate` is published on every pull request head and every merge group head, whatever the changed paths. This is the plan's M1 for one name: required contexts are a subset of what a PR can produce.
| G3 | No pass on absence. If a required check did not run, the verdict is `fail`.
| G4 | No under-declaration. For every capability detected in the tree, the checks of that capability are required, whatever the repo declares.
| G5 | Monotone waiver. A deviation only moves a check to `waived`. It never adds a check to the required set and never changes another check's state.
| G6 | One name. After the cutover, the set of required contexts of a repo is exactly `{estate-gate}` plus the contexts in the kept-context list (section 11).
