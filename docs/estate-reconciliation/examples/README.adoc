= Examples quoted by the Estate Reconciliation specifications

These files are samples, not live deeds. Each has an `.example` suffix so that `deed-conformance` and other tooling skip it, and so that no tool finds a file named `estate_chora.deed` or `ATLAS.deed` here and takes it for the real one.

To lint a deed sample, copy it to the name shown in its specification and run the validator:

[source,sh]
----
cp docs/estate-reconciliation/examples/a2-mytool_chora.deed.example /tmp/mytool_chora.deed
bun 1-formats/deed/tools/deed_lint.js /tmp/mytool_chora.deed
----

The samples carry identities as the opaque literal `#uuid"..."` (ruling U4), which `deed.abnf` v1.3.0 adopted in #1473. The linter accepts it as written.

All deed samples except `a1-federation-root-syntax_chora.deed.example` were checked as written with `deed_lint.js` on 2026-11-12 and passed. That one shows the forge root's syntax under an `estate-deed` head, because v1.3.0 has no forge head yet. The linter therefore reports a head/filename mismatch for it [M]. The ids in them are computed by the recipes in A1 section 9 and are illustrative, not registered. The linter checks syntax and the document head only. It does not check the semantic rules of A1 to A5.

`a1-federation-root-syntax_chora.deed.example` shows the shape of the federation root under the head `estate-deed`, because the current linter does not accept the proposed `forge-deed` head (A1 section 7.1). Its real head and filename are `forge-deed` and `federation_forge.deed`, after the grammar change is approved.

The JSON samples are illustrations and are not validated against the in-toto or DSSE schemas.
