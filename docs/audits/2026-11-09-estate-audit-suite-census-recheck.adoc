== Why this exists

A historical census names `hyperpolymath/standards` as a repository that either
copies an estate-audit composite from before the `fa71ac2a`-era fixes
(2026-09-22), or carries an `actions.lock` entry for the suite that no longer
matches its own workflow references. Census artefacts age badly: this
repository was transferred to `metadatastician/standards`, its workflow set was
rewritten, and the suite itself moved from `hyperpolymath/cicd-suite` to
`hyperpolymath/proven-cicd-and-workflows`. This document is the recheck, taken
against the *current* default branch and the *current* CI, so a later reader can
tell a stale census row from a live defect.

Nothing was edited to produce it. Every number below was read from the tree at
`9bdf864c` or from the GitHub API on 2026-11-09.

== Verdict

This repository is *not affected by either limb*, so no workflow edit and no
lock regeneration is required:

. It *does not reference the estate-audit suite at all* — no `uses:` to
  `hyperpolymath/cicd-suite`, to its successor
  `hyperpolymath/proven-cicd-and-workflows`, or to any of their 26 composite
  gates, anywhere in `.github/`.
. Its `actions.lock` *carries no suite entry*, so there is no entry that could
  disagree with a workflow reference.

The census row is stale because it describes a different repository and a
different era, not because this one was repaired quietly. <<what-the-census-was-measuring>>
names the repository it does describe, and `rsr-template-repo` is still correct
in its own right.

== What the census was measuring, and why the row no longer applies

The census row is not wrong about the estate; it is wrong about *this
repository*, in three separable ways.

*Wrong repository.* The live consumer of the suite is
`hyperpolymath/rsr-template-repo`, whose `.github/workflows/main-estate-audit.yml`
checks out `hyperpolymath/cicd-suite` at `bf7dd95cf497…` (2026-10-19) and runs
six gates from it. That pin is *19 commits ahead of* `fa71ac2a` and therefore
already carries the fixes; measured at `bf7dd95c`, `required-files-check`
contains the `set +e` guard the fix commit introduced (0 occurrences at
`55556cf5`, 1 at `fa71ac2a`, 1 at `bf7dd95c`). The census entry that named
"pre-`fa71ac2a` composites" described the *previous* pin (`55556cf5`, 2026-09-19),
which `rsr-template-repo` has since left behind. `config/rulesets/gates.json`
still lists `main-estate-audit.yml` under `never_required_workflows`, which is
consistent with it being a template-repository gate and never a context this
repository must publish.

*Wrong era.* `.machine_readable/estate-board.tsv` and
`.machine_readable/estate-residue-ledger.tsv` are stamped
`2026-09-15T08:58:14Z`, from a `census-n440` posture run over local checkouts.
At that timestamp this repository was still `hyperpolymath/standards` with 48
workflow files; it now has 71 under a transferred slug. The ledger's one row for
it — `hyperpolymath/standards  UNPINNED-REUSABLE  7` — counts 7 reusable `uses:`
whose `@ref` is not a 40-hex SHA. That count is reproducible *today* only if
comment lines are read as code: this tree holds *21* commented-out `uses:`
examples pointing at `hyperpolymath/standards/…@<sha>` and `@<n>` placeholders
(the `571cc734…` documentation examples), and the YAML-aware gates that replaced
line-grepping — `validate-actions-lock.sh`, `check-lock-pin-contract.sh`,
`check-reusable-closure.sh`, all of which cite YAML-POLICY Y-1 for exactly this
reason — see *0* unpinned remote refs. `docs/reorg/2026-10-14-tidy/wiring-audit.adoc`
records the same trap in the other direction: its author's `yq` was "not Go yq"
and every selfcheck SHA read `UNEXAMINED`.

*Wrong owner of the finding.* The suite itself has moved on: its gates now live
in `hyperpolymath/proven-cicd-and-workflows` (the old slug redirects there), and
its `main-estate-audit.yml` at `c519c452…` (2026-10-28) runs *five component
check runs* — `governance`, `hygiene`, `manifests`, `languages`, `advisory` —
instead of one job of 26 steps, and has dropped the pass-on-absence gates
(`custom-tools`, `contractile-validation`, `proof-runner`) and the two stubs
(`prat`, `semantic-audit`). Whatever this repository might adopt later, copying
or pinning "the 26-composite workflow" would be adopting a shape the suite has
already retired.

== What was changed, and what was deliberately not

* *No workflow edit.* There is no suite reference to repair, and inventing one
  in order to "fix" a census row would add an unreviewed dependency to a
  repository whose startup contract is measured and green.
* *No lock regeneration.* The lock matches the workflows; regenerating it would
  produce a byte-identical file and would be the kind of no-op churn
  `dependabot-lock-regen.yml` exists to prevent.
* *No required-check change.* Both retained lock contexts already start and
  execute at the default branch.
* *This document only.*

If a future change *does* add a suite reference, the binding rules are already in
the tree: pin the callee at a *branch-reachable full commit SHA* (never a blob
SHA — `check-action-pins-resolve.sh` fails `NOT-ANCESTOR`, and `lock-selfcheck.sh`
separates internal consistency from remote reachability), and regenerate
`actions.lock` with the supported tool in the *same* change
(`update-actions-lock.sh` / `gh actions-lock`, extension pinned `v0.2.0` as
`governance-reusable.yml` and `dependabot-lock-regen.yml` install it) rather than
hand-editing it. `docs/ACTIONS-LOCK-CLOSURE-POLICY.adoc` states the same
obligation from the caller side.

== Limits of this recheck

* It is a statement about `9bdf864c` on 2026-11-09. Workflow and lock facts move;
  re-run the table above rather than quoting it.
* It did not execute the suite. It establishes that this repository does not
  reference it, not that the suite's gates are correct.
* It did not read branch-protection rules directly — the token available here
  gets `403 Resource not accessible by integration` on
  `GET /branches/main/protection`. The required-context claim therefore rests on
  CI evidence: both lock contexts report `success` with their steps executed at
  the default branch, and `required-contexts.yml` (which does read the ruleset)
  concluded `success` at the same SHA.
* Two scheduled workflows are red at `9bdf864c` — `Settings Drift Detect`
  (`Scan estate for settings drift`) and `📅 Debt measure` (`Surface a breach
  without minting an issue`). Both are estate-surface measurements, not lock or
  suite defects, and neither is a required context; they are recorded here so
  this document is not mistaken for a claim that all of CI is green.
