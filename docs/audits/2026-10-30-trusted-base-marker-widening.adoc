== Why this exists

`scripts/check-trusted-base.sh` detected Agda assumptions with one pattern:
`^postulate`. A development can be postulate-free and still be unsound — an Agda
`{-# TERMINATING #-}`, a `--type-in-type`, a `{!!}` hole, `primTrustMe`, a Lean
`@[implemented_by]` or `native_decide`, a Coq `Parameter`, an Idris2 `?hole`.
Every one of those makes "proved" mean something weaker than the reader thinks.

This document is the *measurement* half of that change. It records what the
proposed marker set finds across the repositories that call the governance
bundle, what the numbers do and do not mean, how enforcement is rolled out
per repository, which callers need a pin bump to see any of it, and one doctrine
question that is deliberately left open.

Detection changed first and enforcement second, in that order, on purpose. The
policy text is in the :policy:[Trusted-Base Reduction Policy] § "Extended tier".

== Method, and its limits

I say "survey" and not "census" because GitHub code search is a *proxy*. Three
measured facts about that proxy, each of which changes how the numbers below
should be read:

. **It is scoped to the token.** A fine-grained app token granted one repository
   surveys one repository, and its zero is indistinguishable from a real zero.
   The first attempt in this sandbox — with a token that could see one
   repository — produced "0 callers, 0 hits", which is exactly what a clean
   estate would also produce. The survey script now probes scope and exits 2
   with `NEEDS-SCOPE` rather than publishing that.
. **It is not stable between runs.** The same caller query returned *914* and
   then *1,184* results within the same session. Indexing is eventual.
. **It is capped at 1,000 results per query.** The caller query exceeded the cap
   in both runs. The caller set below is therefore a *lower bound*, and the
   script prints `truncated` next to any query that hit the ceiling instead of
   presenting the clipped number as complete.

Consequences applied throughout: every count is labelled with its query status;
markers that cannot be expressed as a search are listed as `not-expressed`
rather than dropped; and the per-repository table is built from *all* visible
repositories with caller status as a column, so a truncated caller query cannot
silently remove a repository from the finding set.

A checkout-based run of `check-trusted-base.sh` inside each repository remains
the authoritative measurement. This survey decides *where to look first* and
*what number to start a budget at*; it does not decide whether a repository is
sound.

== What the numbers do not mean

* **They are not a defect count.** A `{-# TERMINATING #-}` with a written
  termination argument is the pragma working as designed. The count is the size
  of the conversation.
* **`postulate` in `*/proofs/agda/reject/` is a negative control**, not a hole.
  Several Julia packages carry `reject/Postulate.agda` fixtures whose whole
  purpose is to be rejected by their own gate. These are the repositories most
  likely to be red-boarded by a naive widening, and the least deserving of it.
  Their correct disposition is `.trusted-base-ignore`, scoped to the fixture
  directory — which is what the mechanism is for.
* **A file count is not an effort estimate.** Five `believe_me` in one module
  that share one extraction boundary are one decision, not five.

== Rollout

Nothing is enabled estate-wide by this change. Per repository, in this order:

. **Report (automatic).** Every caller that bumps its pin gets `report` mode by
   default: findings printed, `::warning file=…,line=…` annotations on the pull
   request, exit 0.
. **Triage.** For each finding, choose a disposition: discharge (fix),
   `TRUSTED:` + refutation budget (§b), `AXIOM:` + citation (§c), `JUSTIFIED:`
   + written argument (§c-adjacent, the `{-# TERMINATING #-}` case),
   `DEBT:` + owner + date (§d), or a scoped `.trusted-base-ignore` path for
   negative-control fixtures.
. **Budget.** Commit `.trusted-base-budget` with `mode: budget` and the
   *post-triage* number. It may only go down.
. **Strict.** Once the number is zero, switch to `mode: strict`, which is the
   same thing as a budget of zero but reads as an intent.

Repositories with real proof developments should go first, because they are the
ones the gate is for: `EpistemicTypes.jl` (epistemic-types), `firmboot`,
`kitchenspeak`, `ResidualEvidenceTypes.jl` (residual-evidence-types) and
`JuliaPackageSpitter.jl`. They are also the five least likely to be homogeneous,
which is the point: `JuliaPackageSpitter.jl` imports nothing and runs Agda under
`--safe --without-K --double-check --ignore-interfaces -W error` with a
builtin-only Prelude, while a repository using `agda-stdlib` cannot use
`--no-libraries` and is not `--safe`-compatible in the same way. Its *flags* are
not the standard; its *discipline* is.

== Pin-bump list, and why nothing propagates

Reusable workflows are pinned by full SHA in callers. Merging this change to
`standards` changes the behaviour of exactly one set of repositories: those that
bump `governance-reusable.yml` to a revision at or after the merge. Everyone
else keeps the detector they pinned, which is the intended property — a
standards push must not silently change the enforcement running in 400
repositories.

The `trusted-base` job checks out the script at
`${{ job.workflow_sha }}` — the caller's pin — so the script and the workflow
move together. There is no second pin to bump for this job.

=== Producing the list

[source,bash]
----
# 1. the caller set and their current pins (writes pins.tsv; ~2 API calls/caller)
bash scripts/estate-trusted-base-survey.sh --owner hyperpolymath --pins

# 2. open a bump PR per caller (dry-run by default; --fix stages the edit only)
bash scripts/propagate-workflow-pins.sh --to <merge-commit-sha>
----

`pins.tsv` from the survey is the authoritative bump list for the run:
`repo`, `workflow`, `pinned-sha`. A caller is in scope for this change iff its
`governance-reusable.yml` pin is an ancestor of the merge commit, which
`scripts/lib/pin-ancestry.sh` decides — the same assertion every pin bumper
uses.

Note that the pin census reads **both owner spellings** of this repository,
`metadatastician/standards` and `hyperpolymath/standards`. The first run matched
one and reported 306 callers with zero pins; nothing about that output
distinguished "nobody pins anything" from "the pattern was wrong".

Bumping the governance pin for this change must not silently move the
secret-scanner pin, and vice versa: they are independent decisions with
independent blast radii, and a tool that rewrites "all standards pins to one
SHA" would hide the second decision inside the first. Bump one, review, bump the
other. `scripts/propagate-workflow-pins.sh` rewrites every standards pin at or
behind the target, which is the right default for a routine catch-up and the
wrong tool for a targeted bump — use `--to` with a review, not a sweep.

=== If a check's name has to change

It does not here. The `trusted-base` job keeps its key and its name
(`Trusted-base reduction policy`), so every caller's required context string
(`<caller job key> / Trusted-base reduction policy`) stays valid. Any future
rename must follow :signal:[CI/CD Signal Discipline] § "Changing a check safely"
— add, require both, drop the old requirement, remove the old context — and must
never rename and re-require in one step.

The same discipline applies with force to `secret-scanner.yml`, whose own header
records that the job key MUST stay `scan` because the estate-wide
Secret-Scan-Floor ruleset requires the context `scan / gitleaks`. Renaming that
job is not a local edit; it is a change to a required context in every
repository that has the ruleset.

== Doctrine gap raised, not resolved: the language policy checks artefacts, not toolchains

Raised as a question, not applied. The estate language policy bans Python by
running, in `governance-reusable.yml`:

[source,bash]
----
PY_FILES=$(git ls-files '*.py' | grep -v venv | grep -v __pycache__ || [ $? -eq 1 ])
----

That is a check on tracked *artefacts*. It says nothing about **toolchain
declarations**, and the gap is not hypothetical:
`JuliaPackageSpitter.jl` ships a `mise.toml` declaring `python`, `pytest`,
`black`, `ruff` and `isort` and passes the gate, because it tracks zero `.py`
files.

Generalising the question:

[cols="2,2",options="header"]
|===
| Declaration surface | Would the current gate see it?

| `mise.toml` / `.tool-versions` | no — not a `.py` file
| `devcontainer.json` image + features | no
| `guix.scm`, `flake.nix`, `Containerfile` / `Dockerfile` package lists | no
| `Justfile` / `Mustfile` recipe bodies invoking `python -m …` | no
| `pyproject.toml`, `requirements.txt`, `Pipfile` | no
| Poetry/uv lock files | no
| `package.json` scripts invoking Python | no
|==

So: **does the policy intend to cover these?** The honest answer is that
nobody has decided, and the decision is not small:

* If it *does*, it applies to ~416 repositories, most of which are not Julia,
  and many of which legitimately use Python at arm's length (a documentation
  tool, a CI helper, a data reduction step) without shipping a line of it. A
  blanket failure would red the estate on day one and be ignored.
* If it *does not*, then the ban is about what is committed as source, and the
  gate should say so in one sentence, so that the next reviewer does not read
  "Python is fully banned — no exceptions" and conclude that the `mise.toml` is
  a violation.

Either way the shape of the answer is already known from this document: extend
detection and the disposition machinery *together*, report-and-budget anything
new, and never fail-on-sight across an estate that is not homogeneous. The
trusted-base tiering is the template.

=== One correction offered to the request that produced this document

The request listed `%default total` as an Idris2 escape hatch alongside
`assert_total` and `believe_me`. It is the opposite: `%default total` makes the
totality checker mandatory, and `%default partial` is the hole. Detecting
`%default total` would have red-boarded precisely the well-disciplined Idris2
repositories in the estate. It is not detected, and
`scripts/tests/check-trusted-base-test.sh` asserts that it is not — the
assertion runs in the "deliberately not detected" family, which is as
load-bearing as the detection family.

The same reasoning removed `Hypothesis` and `Variable` from the Coq set: inside
a `Section` they are binders discharged at `Qed`, not axioms, and a text scan
cannot tell them apart from a file-scope axiom without a parser.

== Rollback

Every piece is independently reversible:

* **A repository** returns to the old detector by leaving its pin alone. No
  action, no revert.
* **A single repository** sets `--extended-mode=report` in its budget file (or
  deletes the file) and the extended tier stops being able to fail it. The core
  tier is untouched.
* **The estate** reverts `scripts/check-trusted-base.sh` in one commit; callers
  that had already bumped fall back to the previous behaviour on their next
  pin bump, and in the meantime the script they pinned still reports the core
  tier exactly as before.
* **The survey** writes only local files. There is nothing to roll back.
