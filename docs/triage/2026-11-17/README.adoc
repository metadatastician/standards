== What this is

The owner asked three things on 2026-11-17: how to get the estate standards
automated as far as possible; which open issues are stale, which have a small
piece that can be done now, and how to regroup the rest; and to do it with
Scaffoldia, not `rsr-template-repo`, as the way forward.

This page is the plan and the record of that pass. Every count in it comes
from the data files beside it or from a command named in the text. Claims
about other repositories that were not re-measured are marked as such in the
data (`not checked`), and no old estate-wide number is restated here as
current.

Data files (I-JSON, JCS, one record per line):

* `verdicts-standards.jsonl`: one verdict per open issue (206), with evidence.
* `verdicts-template-and-scaffoldia.jsonl`: the same for 19 template issues
  and 1 Scaffoldia issue.
* `move-out.jsonl`: destination per estate-labelled issue (141).
* `open-prs.jsonl`: state of the 34 open pull requests in four repositories.
* `ledger-rows-rsr-template-repo.jsonl`: 5 evidence rows that belong in the
  template's own ledger once it has one.

In this page and in `verdicts-standards.jsonl` the debt-marker words are
written with a hyphen (TO-DO, FIX-ME), so that these records are not
themselves counted by the `todo-fixme-markers` probe, which counts any file
containing the word. One quoted command is affected (the evidence for #401);
the command as run used the unhyphenated word. For the same reason of not tripping a
gate on a quotation, two deprecated names that issue text uses are replaced
in the data by a bracketed description: the old six-file name for the
descriptiles, and the legacy name of the bot-directives directory.

== The answer: three substitutions

Each recurring failure has the same cure: stop keeping a second copy of a
fact by hand, and derive it.

[cols="2,3,3,3",options="header"]
|===
| What keeps failing | Replace it with | Instrument | State on 2026-11-17

| Issue state kept by memory
| Issue state as a function of evidence on `main`
| `scripts/issue-evidence.sh` and its ledger (`3-practice/ISSUE-EVIDENCE.adoc`)
| Built and tested (139 tests); 40 rows; report-only until the owner enables it

| A file copied into N repositories and then drifting
| One source, and a plan that re-derives each copy and shows the difference
| Scaffoldia: a planner produces a plan, a small kernel checks and applies it
| Kernel spike passes 47 of 47 `L0` cases; no planner yet (scaffoldia#76)

| A rule checked by several partial regexes that disagree
| One classifier with a closed vocabulary; the check is "regenerate and compare"
| See work orders E1, E2, E4 below
| One instance done (`scripts/check-pin-comments.sh`); the rest open

| A measurement written into an issue once
| A number recomputed on a schedule that may only fall
| The pattern issue #803 uses; the Debtfile ratchet
| Two estate probes exist; eleven issues should become probes

| A retired format waiting on hand conversion
| A translator that fails closed, plus a mechanical "may this file go" check
| kyX
| Builds; 39 of 39 tests; one family of about ten translates
|===

The architecture that follows from this, as decided today:

* *Scaffoldia* is the repository designer: mint, provision, configure,
  retrofit. `rsr-template-repo` becomes one of its inputs (a spine and packs,
  as data). Nothing new is to depend on the template's mint scripts.
* *The hybrid automation router (HAR)* already has the model Scaffoldia
  needs: a declarative resource graph, an imperative plan, provenance and
  ownership handoff. Minting lowers a graph to a plan; retrofit lifts the
  observed repository, compares and lowers the difference. HAR's 115 tests
  pass at `0176b7d`. Scaffoldia consumes HAR as a pinned module; the plan
  kernel moves to HAR when HAR has a plan level.
* *Two sizes, one system.* A minimal engine is the kernel plus published
  plans, for someone with a few repositories. The composer is a planner on
  the same kernel.
* *No separate control-plane repository.* Scaffoldia owns birth and
  enrolment, chora-registry the census and de-registration, HAR the events
  and plans, gitbot-fleet the acting.
* *Deed and JSON are different kinds of thing.* A deed attests facts. A plan
  is a computed message. One carrier each: deed clauses, and I-JSON/JCS.
