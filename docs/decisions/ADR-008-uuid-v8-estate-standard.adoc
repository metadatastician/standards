== The request

The owner asked that the standards state UUID version 8 as the estate format and
that an estate-wide campaign be planned to move every repository to it.

This record exists because the request reverses a standard that is six days
old, and the change procedure does not let a binding standard be replaced by
an edit. It writes down the request, the design that makes it workable, the
costs, and the campaign. It performs none of the later steps.

== Context: what version 8 is, and what it is not

RFC 9562 numbers UUID *layouts*, not generations. Version 8 is not "newer
version 7". It is the RFC's *custom* layout: the RFC fixes only the 4-bit
version field (`8`) and the 2-bit variant (`10`), and leaves the meaning of the
other 122 bits to the implementation. The RFC recommends version 7 for new
time-ordered identifiers.

So "v8 everywhere" is only an identifier *format* once the estate says what its
122 bits mean. Without that, every repository invents its own layout, and two
v8 values from two repositories can no longer be compared, ordered or
validated beyond the version nibble. This record therefore defines the
estate's v8 layouts. That definition is the substance of the proposal.

What prompted the request: `metadatastician/berrywiki` already mints v8 for
content-derived import ids (`crates/berrywiki-import/src/marker.rs`:
SHA-256 of a domain-separated marker, first 16 bytes, version and variant
set). Re-importing the same CherryTree notebook reproduces the same page ids,
which is what makes re-import idempotent. Version 7 cannot express that.
`ESTATE-UUID-V7` has no clause for deterministic identifiers at all; DEED and
ANCHOR's `#u5` (UUIDv5, SHA-1) literals already sit outside it.

== Proposed decision

All UUIDs created, persisted, exchanged or exposed by an estate repository
MUST be version 8, variant `10`, under exactly one of the two estate profiles
below. Lowercase canonical `8-4-4-4-12` text, as before.

=== Profile T: time-ordered (replaces v7)

Bit-for-bit the RFC 9562 §5.7 version 7 layout, with the version nibble set to
`8`:

----
 48 bits  unix_ts_ms   big-endian Unix epoch milliseconds
  4 bits  ver          0b1000 (8)
 12 bits  rand_a       CSPRNG, or the RFC 9562 §6.2 monotonic counter
  2 bits  var          0b10
 62 bits  rand_b       CSPRNG
----

Every v7 generation rule carries over unchanged: a CSPRNG for the random bits,
monotonicity within a millisecond where ordering matters, and the timestamp
never used for authorisation or as an audited event time.

Generation: take a well-tested library's v7 output and set the version nibble
to `8`. This is the only bit operation permitted, and it is one shared, tested
function per language, not a per-repository recipe.

=== Profile C: content-derived (replaces v3, v5 and ad-hoc hashing)

----
 bytes 0..15 of SHA-256( domain ":" name )
 then: byte 6 high nibble = 0b1000 (ver 8); byte 8 top two bits = 0b10 (var)
----

`domain` is a registered, repository-unique ASCII string (for example
`berrywiki-import`) that MUST NOT contain `:`. It separates the uses so that one
name hashed for two purposes cannot collide. Because `domain` has no `:`, the
first `:` in the preimage always ends it, so two distinct (domain, name) pairs
never hash the same bytes. `name` is unconstrained.
Profile C ids are reproducible by design: the same domain and name always
give the same id. They are not secret and must not be
used where unpredictability is required.

=== Distinguishing the profiles

A v8 value does not say which profile produced it, and this proposal does not
spend id bits to make it do so. The profile is part of the field's declared
type: a schema, API contract or metadata key that holds a v8 id MUST state
`profile T` or `profile C`. Open question Q1 records the alternative.

== Costs the owner accepted

Put to the owner before the ruling:

. *A second migration within weeks of the first.* `ESTATE-UUID-V7` (effective
  2026-09-29) is mid-migration. Mitigation: a v7 value maps to profile T by
  flipping one nibble, reversibly, so a v7 -> v8 alias is a pure function and
  needs no stored mapping table.
. *Library support.* Few libraries mint v8 directly. Profile T depends on the
  shared nibble-flip wrapper; profile C is a few lines over SHA-256.
. *External validators.* Systems that accept only v4 or v7 will reject v8.
  External boundaries keep their own formats under the existing "preserve and
  type explicitly" rule.
. *Self-description.* A reader cannot tell T from C from the bits alone (Q1).
. *DEED and ANCHOR.* `#u5` literals would become profile C. That is a format
  change in two specifications with their own grammars (`anchor.abnf`), and
  needs its own record.

== Alternatives considered

. *Keep v7 and add a deterministic-id clause* (v8 profile C only where
  content-derived ids are needed). Smaller and keeps RFC alignment. Not chosen
  by the owner.
. *Strict v7; BerryWiki dedupes imports through its stored marker.* Loses
  reproducible import ids. Not chosen.

== Campaign plan (planned, not started)

End-condition, per `AGENTS.md` §5e: the repository set is the estate census of
*live, non-archived source repositories*, measured 2026-10-05T13:38Z as
*401 (hyperpolymath) + 58 (metadatastician) = 459*, re-measured at campaign
start with the census revision recorded. The campaign stops when every one of
them has a migration record in state `complete` or `excluded`. `not checked`,
`unknown`, `partial` and `blocked` remain non-success states, as in
`ESTATE-UUID-V7`.

Phases, each its own increment that leaves `main` green (ADR-006):

. *P0, ratify.* Steps 2-6 of the change procedure on this record. Nothing below
  starts before P0 completes.
. *P1, tooling.* `scripts/check-uuid-v8.sh` (version `8`, variant `10`,
  profile declared), the Hypatia rule, the governance-reusable job, shared
  profile T and C generators per estate language (Rust, Zig, Elixir, Julia,
  Bun/JS for existing JS), and their tests, including planted negatives.
  `check-uuid-v7.sh` keeps running until P4.
. *P2, dual-accept.* Write boundaries accept v7 and v8 and emit v8. Every v7
  read is aliased to profile T by the nibble flip.
. *P3, repository migration.* Per repository, in census order, with a
  migration record: inventory, classify, convert literals and fixtures,
  convert generators, post-cutover scan. Batches are capped by the AGENTS.md
  §5e session limit; findings go to `dev-notes/inbox/findings.md`.
. *P4, retire v7.* Remove v7 acceptance and `check-uuid-v7.sh` only once every
  in-scope repository is `complete` or `excluded`.

Known first entry for P3: `metadatastician/berrywiki`. Its import ids are
already profile C, apart from the domain-registration step. Its page ids are
v7 minted by hand from `std::collections::hash_map::RandomState`, which is
not a CSPRNG. That already breaks `ESTATE-UUID-V7` (hand-rolled bits,
non-CSPRNG randomness) and will need fixing under either standard.

== Open questions for review

. *Q1: profile in the bits?* Reserve the top bit of `rand_a` (profile T) or
  of the hash (profile C) as a profile flag, costing one bit of entropy, so
  ids self-describe. Recommended: no; declare the profile in the type, as
  above.
. *Q2: DEED and ANCHOR `#u5`:* migrate to profile C in this campaign, or
  leave them as an external-format exception? Recommended: separate record.
. *Q3: profile C hash:* SHA-256 as proposed, or BLAKE3 for speed?
  Recommended: SHA-256, since it is already used in BerryWiki and is in
  every standard library.

[[decision-record]]
== Decision record (CHANGE-PROCEDURE step 5)

*Decision.* The proposal was adopted as written by owner ruling D305
(2026-10-06), recorded on `hyperpolymath/standards#787`. D305b widened it:
version 8 applies to *every* estate identifier. No identifier class stays on
version 7, and the v7/v8 split some drafts assumed is retired. The owner ruled
directly, so steps 3 and 4 (domain review and a contest period) were not
carried out as separate steps. This record does not claim they were.

*Open questions, as ruled.*

* Q1 (profile in the bits): the recommendation is adopted. The profile is
  declared in the type and is not encoded in the bits.
* Q3 (profile C hash): the recommendation is adopted. Profile C uses SHA-256.
* Q2 (DEED and ANCHOR `#u5`): answered for DEED only. D305 folds deed `#u5`
  into the version 8 profile (profile C). This lands as its own increment,
  together with the `deed.abnf` / README alignment (D308), because it changes
  the value of every existing deed identifier. ANCHOR `#u5` is still open.

*Dissent.* None recorded.

*Effective version.* `ESTATE-UUID-V8` 1.0.0. Its hash is the merge commit of
the pull request that carries this section.

*What this increment ships (P1, first part, and the P2 gate).*

* `scripts/check-uuid-v8.sh` checks UUID literals.
** By default (dual-accept, P2) it accepts version 8 and version 7 with
   variant `10`.
** `--strict` accepts version 8 only.
** It checks every UUID on a line, not only the last one, and a missing scan
   path is an error. The v7 checker did neither; see the rollback limits below.
** It cannot see which profile an identifier uses. That check belongs to
   type-aware tests, as in the profiles section above.
* `scripts/tests/uuid-v8-test.sh` gives the checker known-answer controls and
  planted negatives in both modes.
* The dogfood workflow (`uuid-v7.yml`) and the `uuid-v7-conformance` job of
  `governance-reusable.yml` both run the new checker. Their workflow, job ids
  and job names are left unchanged, so no required status context moves.
  They are renamed in stages; see the two-stage rename amendment of
  2026-10-14 below.

*Superseded material and its retirement.*

* `docs/UUID-V7-ESTATE-STANDARD.adoc` carries a superseded banner. Its
  migration-record states and register shape stay in force for this campaign.
* `scripts/check-uuid-v7.sh` stays in the tree until P4. The P1 plan said it
  "keeps running"; in practice the CI gates now run the dual-accept checker,
  which accepts everything the v7 checker accepts. The only remaining caller
  is the manual `scripts/estate-uuid-v7-audit.sh`, which still measures
  strict v7 conformance and is left as it is. No other repository vendors the
  v7 checker (local grep of the checked-out trees of all 525 local estate
  clones, 2026-10-06; estate callers reach it only through the reusable).
* `HYP-UUID-001` and the machine-readable twin of the v7 standard are *not*
  updated here. Both are `.a2ml` files, and A2ML is retired, so their
  replacement belongs with the deed migration, not with a new `.a2ml` edit.
  Until then they describe the v7 rule. This is a known lag.

*Migration and rollback limits.* The P2 gate accepts every version and
variant pair the v7 gate accepted, and adds version 8. It is stricter in two
places, both found in review of this record:

* the v7 checker read only the last UUID on a line, so a non-v7 literal
  placed before a v7 one passed. The v8 checker reads every UUID on the line;
* a scan path that does not exist now exits 2. It used to scan nothing and
  pass.

On 2026-10-06 both checkers were run over the checked-out trees of the 478
local estate clones (`hyper-repos/` and `meta-repos/`). No clone that passed
the v7 checker fails the v8 one. One clone, `julia-ecosystem`, has no v7
baseline, because the v7 run timed out at 600 s. So turning the gate on
breaks no measured repository. Rolling back to v7 is clean only until v8
literals appear: after that, reverting makes them fail. A profile T value
maps back to version 7 by the same one-nibble flip. A profile C value has no version 7
counterpart, so once identifiers are minted as profile C (P3), rollback means
keeping them as external identifiers.

[[amendment-d320]]
== Amendment: strict now (owner ruling D320, 2026-10-07)

*Decision.* The owner ruled, through the selection UI, that the gates move
straight to strict: version 8 only, estate-wide, now, rather than at P4. The
owner was told beforehand that about 888 local workflow directories call
`governance-reusable.yml@main`, so the change reaches them on merge, and
chose "flip strict now". D320 also rules:

* *Retired A2ML files are not scanned.* `check-uuid-v8.sh` skips `*.a2ml`
  and `*.a2ml.in`. A2ML is dead and may not be hand-converted (D313); its
  identifiers become version 8 when kyX converts each file into deed. This is
  the only arm that keeps strict-now, deed-first and D313 all true. Without
  it, every repository holding a `CLADE.a2ml` (328 of 334 local copies carry
  a UUIDv5) would be red until kyX exists.
* *Clade identifiers are profile C*, derived in the domain `gv-clade-index`
  from `github.com/<owner>/<name>`. This replaces both the UUIDv5 derivation
  gv-clade-index uses today and the CSPRNG-v7 rule in the clade mapping's P-1.
  The change starts at the source (gv-clade-index), then reaches each
  repository's chora deed once deed admits a version 8 literal.
* *A Julia package's own `uuid` is re-minted as version 8*, not exempted,
  where the package is not registered in General. A registered package is a
  separate question for the owner.

*What this amendment ships.*

* `governance-reusable.yml` (job `uuid-v7-conformance`) and the dogfood
  `uuid-v7.yml` run `check-uuid-v8.sh --strict`. The workflow names, job ids
  and job names are unchanged, so no required status context moves.
* `check-uuid-v8.sh` skips `*.a2ml` and `*.a2ml.in`. The test suite gains four
  cases: both extensions are skipped, and a file merely named after A2ML
  (`a2ml-notes.adoc`) or with a near-miss extension (`.a2mlx`) is still
  checked. Removing the skip fails the first two; widening it to `*a2ml*`
  fails the last two.
* This repository passes `--strict`. Two illustrative literals were flipped to
  version 8 (the axel attestation example, the palimpsest consent-layer
  example), and the clade mapping's P-1 and worked example now state the
  profile C rule instead of quoting a version 7 identifier.

*Shim and rollback (ADR-006).* This is a cutover, and it has no parallel run.
The shim is the reusable's own pinning: it checks out the validator at
`job.workflow_sha`, so a caller pinned to a SHA keeps the behaviour of that
SHA until it bumps. Callers on `@main` change on merge. Rollback is removing
the `--strict` argument in the two workflows, which restores P2 dual-accept;
nothing else changes.

*Measured impact.* Measured on 2026-10-07 over the **default-branch tree** (`git archive origin/HEAD`, refs fetched within a day) of each of the 481 local clones under `hyper-repos/` and `meta-repos/`, so untracked files and side branches do not count. One clone, `julia-ecosystem`, timed out in both modes and is unmeasured. Of the other 480, the checker on standards `main` (dual-accept, no A2ML skip) passes 135 and fails 345. This checker with `--strict` passes 296 and fails 184. *168 repos turn green*, almost all because of the A2ML skip. *6 repos turn red*, not counting standards, whose 4 hits this change fixes. Only `kcq` calls the gate at `@main`. It held a v7 literal in two deed files and would have gone red on its next run, but kcq#2 (`4749fd5`) fixed that on its `main`: `--strict` there now exits 0. So no repo goes red on merge. `phantom-metal-taste` (a placeholder UUID in a Julia `Project.toml`), `ZenodoDeposits.jl` (one v7 literal in its tests) and `sim-public-relations` (two literals) pin the gate to a SHA, so each goes red only when it bumps. `berrywiki` and `berrywiki-course-template` call no gate. The other 177 repos fail in both modes. On default branches, 3 repos call `governance-reusable.yml@main`, 357 pin it to a SHA, and 121 do not call it. The figure of about 888 quoted at decision time was not a default-branch count.

*What still follows.* The deed grammar's version 8 literal (`#u8`, whose body
is the profile C preimage `domain:name`), its linter and fixtures, and the
shared profile T and C generators are the next standards increment. The
gv-clade-index derivation change follows it. Each repository then migrates
under P3 as before; strict only means a repository is red until it does.

== Amendment: the profile C domain register (owner answer, 2026-10-14)

Profile C requires a _registered_ domain, but there was no register. Asked
where domains are registered, the owner chose one register in this
repository over per-repository declarations in each chora deed. Per-repository
declarations can only check uniqueness within one repository.

*The register* is `docs/decisions/ADR-008-profile-c-domains.json`. It is
I-JSON in JCS form (JSON-POLICY, D306), and each entry is
`{domain, name, purpose, repos}`:

* `name` says in words what is hashed after `domain:`.
* `repos` lists every repository that mints ids in that domain.

A domain shared by several repositories is a single registration. For
example, `proof-goal` is the cross-tool content address of a proof goal,
which echidnabot and proof-burrower compute the same way, so one goal has one
id in both. Within that one registration the domain is still used for one
purpose only, as ADR-008 requires.

*The check* is `scripts/check-uuid-v8-domains.sh [--registry FILE]
[DOMAIN...]`. It validates the register's bytes (one line, printable ASCII,
JCS, one final LF), the entry shape, the domain rule and strict ordering, so
no domain is registered twice. Given DOMAIN arguments, it also fails on any
that is not registered. A repository that mints profile C ids runs it in CI
against a pinned standards checkout with the domains it uses.
`scripts/tests/check-uuid-v8-domains-test.sh` plants a defect for each rule and
expects each one to fail, for its own reason.

*First entries.* The domains of the P3 pilot repositories are registered
from their current code:

* `echidnabot-proof-obligation`;
* `proof-goal`, shared by echidnabot and proof-burrower;
* `prove-result`.

`gv-clade-index` is registered as ruled in the D320 amendment.
*New ids only* (owner ruling V9, 2026-11-13). From V9 on, new repo
chora ids are minted in the domain `chora-registry`, the registry's new name,
preimage `chora-registry:github.com/<birth owner>/<name>`. An id minted before
V9 keeps its `gv-clade-index` id for good and is re-checked under that domain:
nothing is reminted (rule U1). So `gv-clade-index` stays registered, for
existing ids only, and no new id is minted in it. `chora-registry` is
registered here before any mint uses it.
echidna has no content-id call site yet, so it registers none.
`berrywiki-import` is left for berrywiki to register with its own name form.

== Amendment: the gate takes its v8 name in two stages (owner answer, 2026-10-14)

The gate has checked version 8 only since D320, but it still ran under the v7
names, so a red read "UUID v7 conformance" for a v8 rule. The owner chose to
rename it now, in stages, rather than wait for P4. A one-step rename would
break consumers: live rulesets name `<caller> / UUID v7 conformance`, and a
renamed job would leave that context waiting forever on each repository once
its pin moved past the rename.

. *Stage 1 (this change).* `governance-reusable.yml` gains job
  `uuid-v8-conformance` ("UUID v8 conformance"), the same strict check beside
  the old job, which stays as a deprecated alias. Both names are on the frozen
  list in `tests/test_governance_reusable_shape.sh`. The dogfood workflow
  becomes `uuid-v8.yml` ("UUID v8 conformance" / "Reject non-v8 UUID
  literals"). It is not a gate workflow in `config/rulesets/gates.json`, so no
  derived context moves.
. *Stage 2.* As consumers move their pin past stage 1, re-derive their
  rulesets with `scripts/apply-branch-gates.sh`, so that they require the new
  context.
. *Stage 3.* Once `scripts/check-required-contexts.sh` shows that no consumer
  still requires "UUID v7 conformance", delete `uuid-v7-conformance` and take
  it off the frozen list.

== Amendment: external UUID constants carry a one-line pragma (owner ruling CASE-067, 2026-11-14)

Some UUIDs are not the estate's to choose: a protocol constant (the RFC 6455
WebSocket GUID is version 4), a published test vector, a vendor's id. Before
this amendment the gate's only escapes were `#uuid"…"`, which admits version 5
or 8 only, and the per-file `.uuid-v8-exempt`, which exempts a whole file. So
"type external IDs explicitly" could not be followed for a version 1, 3 or 4
constant, and a whole file had to be exempted for one line.

The owner chose an inline mark, and chose its syntax by selector:

* On the same line as the UUID, in any comment syntax:
  `hypatia: allow uuid/external -- <reason>`.
* Where a format cannot carry a comment on that line, on the line before:
  `hypatia: allow-next-line uuid/external -- <reason>`.
* A format with no comment syntax at all (JSON) keeps the per-file
  `.uuid-v8-exempt`, reviewed in the repository that adds it.

The rules, enforced by `scripts/check-uuid-v8.sh` in both modes and tested by
`scripts/tests/uuid-v8-pragma-test.sh` (also run under mawk):

. The mark exempts the bare-UUID rule on exactly one line.
. It never exempts an identity field (CHORA-SPEC 7.1), a `#u5` identity value
  or a malformed `#uuid` literal.
. The reason is required. A mark without one fails.
. A mark is stale when its line holds no UUID the gate would refuse (the
  constant was removed, or became version 8). A stale mark fails, so marks do
  not pile up unseen.
. A mark whose reason is the literal placeholder `<reason>` is a
  documentation example and is ignored.

Hypatia and cicd-squabbler refer a missing or stale mark. They never write
one: whether a UUID is truly external is a human judgement, and rewriting an
external constant would break the protocol it belongs to.

== What this record does not do

It does not migrate any repository (P3), change the deed grammar, or update
`HYP-UUID-001`. The D320 amendment retires version 7 acceptance at the gates;
P4 is now only the removal of `check-uuid-v7.sh` and the superseded v7
standard once every in-scope repository is `complete` or `excluded`.
