= Fork governance — specification v1.4
:toc: left
:toclevels: 4
:revdate: 2026-11-12
:revnumber: 1.4
:status: normative

This document is normative for the *comment*: its markers, its blocks, their
order, what each may show in public, how they fold, their states, and the rules
the posting job obeys. It is the one layout specification for the pull-request
comment; link:../../docs/REPOSITORY-OBSERVATORY-PROPOSAL.adoc[the Observatory
proposal] defers to it for display. It does not restate how a lane computes its
verdict; that is link:LANES.adoc[LANES] and, for the grids themselves,
link:../../docs/VERDICT-GRID-SPEC.adoc[VERDICT-GRID-SPEC].

Version 1.4 records the owner's layout rulings of 2026-11-12. Read top to
bottom, the comment answers, in order: what matters here (summary card); is the
farm alive and in touch (farm); is this repository still what it says it is
(K9-DEED); does it pass its tests (tests); what did the scanners and the fleet
find (Hypatia); what do we manage, who follows whom and are we in sync (fork
governance, with the line map); and is anything we depend on, or that depends
on us, unwell (dependencies). One folding rule applies to every section (§2.8).

== 1. Terms

*Lane*:: One conformance question with one verdict. This system has exactly
three: DEED syntax, K9-DEED conformance, Hypatia verdict grid.

*Grid*:: The per-row report a lane renders into `report.md`
(VERDICT-GRID-SPEC §Anatomy). Two of the three lanes have one; DEED does not.

*Summary*:: The three-row table at the top of the comment. It is a projection
of the lane verdicts, never an independent judgement.

*Summary card*:: The summary table plus the card facts beneath it (§2.3): the
always-visible top of the comment.

*Block*:: A section of the comment that is not a lane: farm, tests, fork
governance, dependencies, and the external reviewer coverage. A block reports evidence
that another producer owns. It has a state (§2.7) and is shown in the summary
card, but it never sets a lane state or the overall badge (§3.2): the comment
must not become a second gate.

*Posting engine*:: `fork-governance-reusable.yml`. The only component that
writes to a pull request, except on a pull request from a fork (§4.1).

*Publisher*:: `fork-governance-publish-reusable.yml`, called from a
`workflow_run` workflow. It writes the comment the posting engine rendered but
could not post because a fork's run has a read-only token (§4.1).

== 2. The comment contract

=== 2.1 Marker

[source]
----
<!-- fork-governance-verdict: regenerated on every run -->
----

The marker MUST be the first line of the comment body. The posting engine finds
its previous comment by marker *and author*; a comment carrying the marker but
written by any other account MUST be ignored. Without the author check, anyone
who can comment could plant a marker and a forged baseline, and the delta
column of every later revision would be measured against it.

=== 2.2 Order

The body MUST contain, in this order:

. the marker;
. on a comment written by the publisher (a pull request from a fork,
  §4.1) only: the publisher's notice, a single line naming the fork run
  the comment was rendered by. The posting engine never writes it, and a
  scraper that reads by position skips this one line on fork comments;
. the heading `# Fork governance`;
. the summary card (§2.3): the summary table, then the card facts;
. the scope note;
. the block marker `<!-- fork-governance:block farm -->` and the farm line
  (§2.9). Always present;
. the lane marker `<!-- fork-governance:lane k9-deed -->` and the heading
  `## K9-DEED conformance`, then the k9-deed grid or its orange placeholder.
  Always present;
. the block marker `<!-- fork-governance:block tests -->`, the heading
  `## Tests`, then the tests block (§2.10). Always present;
. the lane marker `<!-- fork-governance:lane hypatia -->` and the heading
  `## Hypatia verdict grid`, then the Hypatia grid with the fleet's rows, or
  its orange placeholder. Always present;
. the block marker `<!-- fork-governance:block lineage -->`, the heading
  `## Fork governance`, then the lineage block with the line map (§2.11).
  Always present;
. the block marker `<!-- fork-governance:block dependencies -->`, the heading
  `## Dependencies`, then the dependency walk (§2.12). Always present;
. the block marker `<!-- fork-governance:block reviewers -->` and the external
  reviewer coverage (§2.6).

Order is part of the contract because the sections are read by humans and by
scrapers, and because an order that varies between runs makes two verdicts on
the same PR look like two different verdicts.
`scripts/tests/fork-governance-render-test.sh` asserts it. Scrapers MUST find a
section by its marker, never by its position: v1.4 inserted blocks between the
lanes (§8).

Every section is always present; none is conditional on good news or on the
repository's shape.

The lane *name* is `K9-DEED conformance` in the summary row and in the section
heading. It is not `K9 conformance`; the rename is normative.

The K9-DEED section is the identity-stability check: the descriptiles (the
deed's account of what the repository *is*) still parse, and the K9 runner can
still enforce the contractiles (what it *must* hold). A failure here is the
gravest state in the comment, because it means the repository's own
self-description says that its contracts are broken. Its summary line names
which side failed: the deed (description) or the contracts (enforcement).

=== 2.3 Summary table

[cols="1,1,4",options="header"]
|===
| Header | Values | Rule
| `Lane` | fixed strings | As listed in §2.2.
| `Status` | DEED: `<glyph> <word>`; K9/Hypatia: `<glyph> <word> (job: <result>[; grid: <glyph> <word>])` | Derived from the lane's job result and verdict (§3). If a grid job did not succeed but has a recognised verdict, show that grid verdict after the job result; it does not replace the lane state. Never typed by hand.
| `Status` (suffix) | `· advisory in grid scope: <glyph> <word> (<n> critical, <n> high, not grading)` | Optional, on the Hypatia row only. Present when the grid has advisory rows, even when those rows have zero graded findings (§3.2). Counts include only graded findings in the grid's declared scope; standing/excluded findings remain visible in the grid. Absent — not `none` — only when there are no advisory rows.
| `Run` | `[run N](url)` or `same run` | The first row carries the link; the rest say `same run` because they share one run.
|===

==== 2.3.1 Card facts

Under the table, one line per fact, in this order. The card is highlights
only: each fact is a state and at most a few words, so the card alone answers
"is anything not green?" without opening a section:

[cols="1,4",options="header"]
|===
| Fact | Content
| `Subject` | repository (display name; the forge's repository ID where it exposes one), head commit (12 hex), base commit, PR number. A display name is not an identity.
| `Farm` | the three farm answers (§2.9).
| `Tests` | `<glyph> <word>` of the tests block (§2.10).
| `Fork governance` | `<glyph> <word>`, then `fork of <owner>/<repo>` or `not a fork`, and the sync state (§2.11). Never blank.
| `Dependencies` | `<glyph> <word>` and the count of non-green entries by class (§2.12).
| `Reviewers` | the external reviewer coverage word (§2.6).
|===

The lane states stay in the table; the facts never restate them.

=== 2.4 Embedded grids

The lane reports MUST be embedded verbatim, including each lane's own marker
(`<!-- verdict-grid:k9 … -->`, `<!-- verdict-grid:hypatia … -->`) and its
baseline comment. Two consequences, both intended:

* each lane remains independently machine-readable *inside* the combined
  comment, so the lane's own baseline parser keeps working across revisions;
* a reader who only knows about one lane can still find it.

=== 2.5 A missing lane is a row, not an omission

If a lane produced no artifact, the section MUST contain an orange
`**indeterminate**` line naming the job result, and the summary row MUST be
orange. A lane MUST NOT be dropped from the body or the table.

A summary that silently loses a row reads as "nothing wrong there". That is
the failure mode this system exists to prevent, so it is also the one it must
never itself exhibit.

=== 2.6 External reviewer coverage (advisory)

Last in the comment (§2.2), the posting engine reports a snapshot of external
reviewer coverage for the PR head observed while collecting evidence. This
is not a fourth lane and MUST NOT alter any lane state or overall badge.
A completed review on a different commit, a pending/dismissed review,
a quota failure, or silence MUST NOT be interpreted as a completed review
on the current head. In particular, a quota failure may itself be delivered
as a `COMMENTED` review. A review observed on the head is a coverage fact,
not a claim of approval. Quota notices in issue comments have unknown head
scope. A Codex review summary is the exception: it is an issue comment that
names its commit in its own state marker, so a summary that reports a failed
review for the head is reported as no review on that head. A Codex usage-limit
notice names no commit. API failure or a head change during collection is
indeterminate.
The snapshot is refreshed when the summary runs; it is not live review state.
The advisory may be omitted, with a workflow warning, when it would exceed
the publisher's 65,000-character comment budget. Existing lane reports take
precedence. Older `canon-ref` renderers remain supported; the posting engine
appends the advisory without requiring a new renderer argument.
For external callers, the coverage helper is fetched independently at the
reusable workflow's own commit (`job.workflow_sha`), even when `canon-ref`
selects an older renderer. A failed helper fetch leaves coverage indeterminate.
The implementation reserves 2,048 bytes for the fork publisher notice and
stamp, and uses a conservative byte count. Lane text cannot suppress the
advisory by mentioning its title; the posting engine appends its own section.

=== 2.7 Block states

A block uses the lane state words (§3) with the same glyphs, and the same
rule for missing evidence: a block whose producer did not run, failed, or does
not exist yet is orange `indeterminate` *with the reason*, in the block and in
its card fact. A block is never green by absence of evidence, and never
dropped (§2.5 applies to blocks as it does to lanes). `grey` (`not applicable`)
is a statement about the repository with a reason, never a stand-in for
"not yet built".

A block's state does not feed the lane states or the overall badge (§3.2). It
is evidence other checks own: a failing test suite fails its own required
check, and the comment reports it.

=== 2.8 Folding

One rule for every section. Folding is presentation; it is never a privacy
control (§2.13).

. Always visible, never inside a `<details>`: the heading, the summary card,
  the scope note, the farm line, and every lane and block heading with its
  state.
. Every section body (a lane's embedded grid, a block's content) sits in one
  `<details>` whose `<summary>` repeats the section's `<glyph> <word>`. The
  `<details>` carries `open` exactly when the state is neither green nor grey.
  A green or not-applicable section is folded; anything a reader must act on
  or must distrust is open.
. Inside a section, rows fold as the grid already specifies (VERDICT-GRID-SPEC
  §Anatomy, one `<details>` per row with anything to show). A row's `open`
  follows the same rule as its section.
. The lane markers and the grids' own markers and baseline comments stay
  outside any `<details>` they would otherwise be hidden by, in the order of
  §2.2, so that a marker lookup never depends on rendering.

=== 2.9 Farm (always present)

The farm is the private farm this repository reports to
(`.git-private-farm`). Its line gives three answers and nothing else:

`**Farm:** <glyph> alive · <glyph> working · <glyph> in touch`

[cols="1,3",options="header"]
|===
| Answer | Question
| `alive` | Is the farm's agent running? ("yes, I am working")
| `working` | Is the farm doing its job for this repository? ("yes, it is working")
| `in touch` | Are the farm and this repository connected and current? ("yes, we are in touch")
|===

Each answer is 🟢 yes, 🔴 no, or 🟠 indeterminate (no current evidence, the
producer failed, or the producer does not exist yet). The line is green only
when all three are yes.

Nothing else may appear: no reason, host, URL, issue, identity, count or
timestamp. The reason for any answer that is not yes lives in the owner-only
view (§2.13), which the line may link to only once that view enforces
authentication.

*Departure recorded.* The Observatory proposal made public farm status opt-in
per repository (default deny). The owner ruled on 2026-11-12 that the line is
always present with the state word only. The state word is the whole of what
is public; the detail stays private by default, as the proposal intended.

=== 2.10 Tests (always present)

The test-suite entry point and its result for the head commit: the command or
workflow that runs the suite, and `passed`, `failed`, or `not run`, with counts
where the runner reports them (passed, failed, skipped). A repository with no
suite says `no suite found` (orange: an untested repository is not a green
one). Failing tests are listed first, at most 20, with a count of the rest.

The block reports the suite; it does not run it. Its producer is the
repository's own test job result for the head.

=== 2.11 Fork governance (always present)

What this repository is in its lineage: what is under our management and what
is not, whom we follow and who follows us, and whether each pairing is in sync.
Sometimes we are the terminus of a line, sometimes a station in the middle; we
may be subject to another repository's changes, or others may be subject to
ours. Divergence can be alarming or intended (it may be why the fork exists),
so the block reports it and does not judge it.

The block shows:

* *Management*: for this repository and each station on the map, `ours`
  (under our management) or `theirs`, from the estate register.
* *Upstream* (what we follow): for a forge fork, the parent from the forge's
  fork flag and parent fields; plus any declared upstream. Compared branches,
  ahead and behind counts when the forge can compare them, the last sync it can
  observe, and the inherited-language paths a fork declares (LANES, Lane 3).
* *Downstream* (what follows us): forks of this repository and repositories
  that declare it as their upstream, each with the same sync facts.
* *The line map* (below).

A name, a template origin, a remote URL or a workflow called `fork-governance`
never makes a repository a fork. A repository with no fork and no declared
lineage says `not a fork · no declared lineage` (grey, with that reason). An
unavailable comparison is `indeterminate` with its reason, never zero
divergence.

==== The line map

A London-Underground-style map of the lineage: stations are repositories,
lines are typed relationships, and this repository is highlighted wherever it
sits (terminus or interchange).

Sources, and nothing else:

* *Declared lineage*: the repository's own deed, `(ecosystem)` clause: `:chain`
  and each `(related … :relationship …)`. The deed is the authority for what a
  repository says about itself.
* *Forge facts*: fork flags and parent fields; the forge's compare endpoint for
  ahead and behind counts.
* *Everything else, and every station's state*: the estate register. Cadastra
  observes (what exists and in what state, as found by running the scan);
  reposystem models (the typed graph, imported from cadastra's register and the
  deeds). The block reads reposystem's `estate-json` export. Neither the
  posting engine nor the renderer computes the graph.

Rules:

. A line is drawn only for an observed or declared, typed relationship. Its
  style names the relation: `fork-of`, `mirror-of`, `upstream-of`,
  `template-of`, and reposystem's `uses`, `provides`, `extends`, `replaces`,
  `refers-to`. A forge fork and a mirror are different facts. Nothing is
  inferred from names.
. Each station shows `<name> · <glyph> <word> · ours|theirs · checked <date>`:
  the state of that repository's default branch as cadastra last observed it,
  and when. A station with no observation is orange `?`, never green.
. The map is a Mermaid `flowchart LR` with what we follow to the left of this
  repository and what follows us to the right, at most 12 stations per side,
  with a count of the rest. It is immediately followed by a plain list of the
  same edges (`upstream: standards · standard-source · ours · 🟢 clean ·
  checked 2026-11-12`), so the content survives a client that does not render
  Mermaid and is read in order by a screen reader. The list, not the drawing,
  is the record.
. Until reposystem exports a downstream index and distinct fork and mirror
  relations, the map shows what the deed and the forge state and says
  `downstream: indeterminate (estate register not yet wired)`.

=== 2.12 Dependencies (always present)

A dependency walk, in both directions: what this repository depends on
(packages, direct and transitive, and estate repositories it uses), and what
depends on it. It is a diagnostic, like a medical one: comprehensive, short,
and pointing elsewhere for detail. It does not explain why an upstream is in
the state it is in; it says that it is, and where to read about it.

Each entry has exactly one class, worst first:

[cols="1,1,3",options="header"]
|===
| Class | Glyph | Meaning
| `compromised` | 🟣 | Identified as maliciously altered or under active attack (suspected or confirmed, and says which).
| `vulnerable` | 🔴 | A known CVE or a serious security advisory applies to the resolved version.
| `gone` | 🔴 | Deleted, yanked or unresolvable.
| `incompatible` | 🟡 | Declared or observed incompatible with something this repository also uses.
| `unmaintained` | 🟡 | Archived, or its maintainers have said they will not maintain it.
| `fine` | 🟢 | None of the above, as of the last check.
| `unknown` | 🟠 | No current evidence, or the source failed.
|===

Rules:

. Every entry that is not `fine` carries one marker. `!` means a known, new
  state: the source has announced it. `?` means not certain: the evidence is
  partial and the entry says what is known. The marker is never omitted.
. A non-green entry is a link to the source's announcement (the advisory, the
  archive notice, the registry's yank record), and it carries a one-line
  summary as the link's title, which a reader sees by hovering. The comment
  itself carries no more than that line: whoever needs detail follows the link,
  or asks someone (or an AI) to read it.
. An entry that is also a station on the line map (§2.11) names it, so the
  reader can see where it sits.
. Green entries are counted, not listed, unless the section is opened.
. A missing advisory feed is `unknown`, never zero vulnerabilities. A class is
  never inferred from a repository's name, age or activity alone.

=== 2.13 What is public

The comment is public on a public repository and copied into notifications.
It carries only what is safe for that audience:

* lane and block states, counts, file paths and finding text that the producers
  already publish for this repository;
* for the farm, the three answers alone (§2.9);
* no private URL, host, secret, identity, issue title or farm detail, by
  default and in every block.

Hiding with `<details>`, CSS or a client filter is not a privacy control. What
must not be public is not rendered; the owner-only view (an authenticated
front door, owned by cadastra once it exists) is where detail lives.

== 3. State derivation

The posting engine receives two different facts per lane and MUST NOT confuse
them:

* `*-result` — the *job result* (`success`, `failure`, `cancelled`, `skipped`).
  It says whether the lane completed.
* `*-verdict` — the *grid state* (`green`, `yellow`, `orange`, `red`, `grey`,
  and for findings lanes `purple` or `blue`). It says what the lane found.

Rules, in order:

. If the job result is not `success`, the lane state is `red` for `failure` and
  `orange` for anything else — *regardless of the verdict*. A failed job whose
  artifact still says green is red, because the failure is the newer fact.
. Else, if the verdict is a recognised state word, the lane state is that word.
. Else the lane state is `orange`. An unrecognised or missing verdict is never
  green.

DEED has no grid of its own: its job result is the whole of its verdict
(`success` → green, `failure` → red, anything else → orange).

For K9 and Hypatia, the primary summary state still follows the job-result
rules above. If a non-successful job has already produced a valid grid, the
status MUST show that grid state separately; a red job and a yellow findings
grid are compatible facts, not conflicting verdicts. In particular, the
baseline gate and the grid may grade different scopes, so a blocking gate can
fail on a finding that the delta grid reports as standing or excluded.

=== 3.0 What the verdict is a verdict ABOUT

A lane's state grades *the change*, not the repository. The summary answers
"may this pull request merge", and a finding that predates the pull request is
not evidence about the pull request.

Each row therefore carries three disjoint counts, and only the first grades:

[cols="1,2,3",options="header"]
|===
| Count | Meaning | Grades?

| `counts`
| findings inside the declared scope — the changed files, or the whole tree
  when no scope is declared
| yes

| `counts_standing`
| findings in files this change did not touch
| no — reported, so the number cannot be mistaken for zero

| `counts_excluded`
| findings under a declared exclusion prefix (`9-archive/` by default), and
  banned-language findings on a real fork's declared inherited-language paths
| no — reported, so exclusion is visible rather than silent
|===

A finding with no path is graded: absence of a location is not evidence of
absence of a defect, and the alternative lets a reporter escape the gate by
omitting a field. The duty this puts on producers: a repository-level finding
MUST carry the path it is about (for a missing file, the path where the file is
expected; for a repository property, the file that sets it). Then a change that
does not touch that path reports it as standing, as it should, instead of every
pull request inheriting it.

The scope is part of the report and of the embedded baseline blob. A delta is
comparable only when the previous revision was produced under the same scope —
a change from whole-repository to diff-scoped reporting makes every row look
improved, which is a measurement artefact, not a fix.

The identity line states it, so the reader never has to infer it:
`scope: this change (N file(s)) · excludes \`9-archive/\``, else
`scope: whole repository`.

=== 3.1 Gating and advisory rows

A reporter is *gating* or *advisory*. The lane state is the worst **gating**
row; an advisory row cannot set it, regardless of severity.

Hypatia and pons are gating (owner ruling 2026-11-12: pons gates). panic-attack
is advisory, and so is every fleet member, unless
`.gitbot-fleet/enrolment.json` sets `reporters.<id>.gating` to a boolean, which
overrides the default either way. When the pons row moves to its fleet
adapter (gitbot-fleet `docs/migrations/scanner-cutover-ponsbot-panicbot.adoc`),
the enrolment sets `"gating": true` for `ponsbot`; `panicbot` stays advisory.
During the phase 1 shadow period (14 days from 2026-11-14) both are enrolled
with `"gating": false`, beside the direct panic-attack and pons rows, so a
fault in an adapter cannot block a merge; the flip to `"gating": true` for
`ponsbot` lands with the phase 2 PR that removes the direct pons row. A
grid with no gating row at all falls back to grading every row — never green by
absence of evidence.

The advisory figure beside the verdict (§2.3) exists because the alternative —
omitting advisory findings from the summary — makes a purple critical invisible
on the one line everyone reads. Its critical/high counts cover only the grid's
graded scope; standing and excluded findings remain visible in the reporter rows
and their details. Shown and not grading is a different claim from not shown,
and only the first one is honest.

=== 3.2 The overall badge

`badge.json` carries the *worst* lane, with precedence
`red = purple > orange = blue > yellow > green` and `grey` only when every lane
is grey. Red outranks orange deliberately: missing evidence must not be able to
hide a known failure (VERDICT-GRID-SPEC §Conformance family). Because yellow
can mean either conformance advisory debt or medium findings, its cross-lane
badge message MUST be neutral (`attention`), not a label from one family.

== 4. Posting

. One comment per pull request. The engine lists the PR's comments, selects
   those whose author equals `grid-author` *and* whose body contains the
   marker, takes the last, and PATCHes it. Otherwise it POSTs.
. The marker is read *before* the new body is written, so a rerun cannot create
   a second comment.
. `concurrency.cancel-in-progress` is set on the run: a superseded run that
   finished later would otherwise overwrite a newer verdict with a stale one.
4. The engine runs with `always()`. A lane that failed is exactly when the
   summary matters most, and a summary that does not appear when something
   broke reads as a pass.

=== 4.1 Pull requests from forks

On a pull request from a fork GitHub gives the run a read-only token whatever
the workflow grants, so the posting engine cannot write. It still renders the
comment and the step summary, and uploads `body.md` with
`{pr_number, head_sha, run_id}` as the `fork-governance-comment` artifact
instead of posting.

The publisher runs when the "Fork governance" run completes, from the default
branch's copy of its workflow and with the base repository's token, so nothing
the fork changed runs in it. The artifact was written by the fork's code and is
data, never instructions:

. `pr_number` MUST name an open pull request whose head is the triggering
  run's `head_sha`, `head_repository` and `head_branch`. A run cannot address
  any pull request but its own; a run whose pull request has moved on
  publishes nothing, because the newer run will. (`workflow_run.pull_requests`
  would name the pull request directly, but GitHub leaves it empty for runs
  from forks.)
. The body MUST start with the marker (§2.1) and fit in one comment.
. The publisher uses the same marker-and-author lookup as the posting engine,
  so a pull request still has exactly one comment (§5).
. Only the newest run writes. The publisher stamps the comment with its
  run id and attempt (the comment's last line, never the fork's) and does
  not replace a comment stamped by a newer run of the same pull request.
  Publishers for one fork branch run one at a time.
. A run may leave no artifact only when it was replaced: a newer attempt, or
  a newer run at a different commit of the same fork branch (a push re-runs
  every pull request from the branch). Any other run without one, including
  one cancelled by hand, fails its publisher.
. The body's first line MUST be exactly the marker (§2.1), not merely start
  with it. The publisher's second line names the run the comment was
  rendered by and says it was published from a fork run. It comes before
  any of the fork's text, so nothing in the body (an unclosed HTML comment,
  an open `<details>`) can hide it, as it could hide a footer. The
  publisher cannot make a fork's verdicts honest; branch protection
  requires the lane checks, never the comment (ADOPTION §4).

== 5. Single poster

A repository MUST have exactly one poster for these lanes. The publisher
(§4.1) is not a second poster: it writes only what the posting engine rendered
and could not post, through the same comment. Where a lane's
reusable also posts (some forks call a local copy that does), the repository
MUST disable one of the two. Two comments carrying the same lane but different
runs is two verdicts, and a reader has no way to know which is current.

The estate's lane workflows follow the split in link:LANES.adoc[LANES]: lanes
render and publish artifacts, the posting engine writes. `k9-conformance.yml`
and `hypatia-scan-reusable.yml` therefore request no write permission.

== 6. Permissions

[cols="1,2,3",options="header"]
|===
| Job | Permissions | Why
| `deed` (called reusable)
| `contents: read`
| Lints the caller's tree.
| `k9` (called reusable)
| `contents: read`, `pull-requests: read`
| Reads the previous grid comment for the delta column; writes nothing.
| `hypatia` (called reusable)
| `actions: read`, `contents: read`, `security-events: write`
| Uploads SARIF. A caller may not grant less than the callee declares — the
run then dies at startup with zero jobs.
| `fleet` (plain job)
| `contents: read`
| Checks out gitbot-fleet at a pinned SHA, runs the enrolled adapters on the
head, uploads the `fleet-report-backs` artifact. Not a lane: no grid, no summary
row (LANES, "The fleet report-backs").
| `verdict` (posting engine)
| `contents: read`, `actions: read`, `pull-requests: write`
| Downloads two artifacts, writes one comment. On a fork's pull request the
token is read-only and it uploads the comment instead (§4.1).
| `publish` (publisher, `workflow_run`)
| `actions: read`, `pull-requests: write`
| Downloads the fork run's comment artifact, checks it, writes one comment.
Never checks out code.
|===

The posting engine MUST NOT be given `contents: write`. It has no reason to
touch the tree, and a commenting job with write access to the repository is a
commenting job that can rewrite it.

== 7. Failure semantics

[cols="1,1,3",options="header"]
|===
| Condition | Comment | Run
| All three lanes green | green summary | green
| A lane red | red summary; red row | red (the lane job fails)
| A lane could not run | orange row, orange summary | as the lane reports
| Artifact missing but job green | orange row | green
| Comment could not be posted | none | red — a governance run that cannot report is a failure
| Pull request from a fork | posted by the publisher (§4.1) | as the lanes report; the publisher's own run is red if it cannot post, or if a run that nothing replaced left no comment artifact
| An acknowledgement has passed its `expires_at` | unchanged | as the finding now grades — the entry stops suppressing before the date is noticed
|===

=== 7.1 Acknowledgements are dated, and the date has consequences

An entry in `.hypatia-baseline.json` MUST carry `expires_at`. The gate already
honours the field — a past-dated entry is dropped before matching, so the
finding grades again — which means the date is not paperwork: it is the
mechanism by which a suppressed finding returns.

Three rules follow, and they are enforced in different places on purpose:

[cols="1,2,3",options="header"]
|===
| Rule | Enforced by | Failure mode if it were not

| New or changed entries must be dated, in the future, and within the horizon
| `check-exemption-ratchet.sh` §2b, per pull request
| The escape hatch becomes a way to add permanent debt with a sentence of prose

| Every entry must be dated
| `check-baseline-expiry.sh`, per repository (`baseline-strict`)
| Undated entries accumulate: measured 2026-10-24 at 23 of 63 in this
  repository, seven of them literally "Baseline permanently"

| Soon-expiring entries must be surfaced before they lapse
| `check-baseline-expiry.sh --warn-days`, advisory
| A cliff where many entries lapse at once turns every PR red and the ledger is
  bulk-renewed unread — the ratchet clicked back one notch without a decision
|===

The horizon is 366 days. A date beyond it defers the decision rather than
dating it; a date in the past is a re-acknowledgement of nothing. Both are
refused, because a field that accepts any value records only that someone typed
something.

A missing comment is never acceptable, and never silent: the posting job fails
loudly rather than exiting 0 with nothing to show.

== 8. Compatibility

* The marker strings are a public interface. Changing one orphans every
  existing comment, which then stands as a stale verdict forever.
* Adding a lane is a MINOR change: a new row, a new section, in the documented
  order. Removing or renaming a lane is MAJOR and requires a migration that
  edits or deletes existing comments.
* Consumers must find sections by marker and tolerate sections they do not
  know. v1.4 inserted the farm and tests blocks between the lanes and the fork
  governance, dependencies and reviewer blocks after them: a consumer that read
  the lanes by position breaks, one that reads by marker does not. Adding a
  block is a MINOR change; its marker is a public interface like a lane's.
* A block whose producer does not exist yet ships rendering `indeterminate`
  with that reason (§2.7). It is never held back until the producer exists,
  because a section that appears only when it has good news is not a report.
* Scope and gating (§3.0, §3.1) are a MINOR change to the grid schema, and the
  renderer declares it (`schema: 2`). A consumer that reads `state` cannot
  tell why it changed — diff-scoping and advisory-splitting both only ever make
  a row quieter — so the report carries `scope` and a per-row `gating` flag for
  exactly that reason. Do not remove them as redundant; they are the audit
  trail for every state that got better without a fix.
