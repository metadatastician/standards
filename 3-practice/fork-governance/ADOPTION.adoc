= Fork governance — adopting it in a repository
:toc: left
:toclevels: 3
:revdate: 2026-10-28

This is the operator's guide. It assumes you want the same comment, in the same
order, on every pull request in a repository, and that the repository already
lives in the estate (it has `.machine_readable/`, it may have `.deed` and
`.k9.ncl` files, and the fleet may be enrolled against it).

== 1. What you are turning on

One workflow, five jobs, one comment:

[source,yaml]
----
jobs:
  deed:
    uses: metadatastician/standards/.github/workflows/deed-conformance.yml@<SHA>
  k9:
    uses: metadatastician/standards/.github/workflows/k9-conformance.yml@<SHA>
  fleet:
    uses: hyperpolymath/gitbot-fleet/.github/workflows/fleet-report-back-reusable.yml@<FLEET-SHA>
  hypatia:
    uses: metadatastician/standards/.github/workflows/hypatia-scan-reusable.yml@<SHA>
  verdict:
    uses: metadatastician/standards/.github/workflows/fork-governance-reusable.yml@<SHA>
----

`fleet` is not a lane: it produces the gitbot-fleet report-back envelopes that
the Hypatia lane folds into its grid, one row per member enrolled in
`.gitbot-fleet/enrolment.json`, and uploads them as the `fleet-report-backs`
artifact. Without it every enrolled row reads orange, "enrolled, but no
report-back was received". See <<fleet>>.

The three lanes produce verdicts and artifacts. The posting engine reads them from the
caller's `needs` graph — a reusable cannot see your jobs, so you pass the
results in — and writes the comment.

== 1.1 Prerequisite: cross-owner Actions policy

A reusable workflow is resolved against the *caller's* effective Actions
policy before any job is started. For a caller outside `metadatastician`,
ensure its `selected actions and reusable workflows` list permits
`metadatastician/standards/.github/workflows/*@*` and every other required
reusable (including `hyperpolymath/gitbot-fleet` where used). A working git
checkout or REST redirect does not prove a remote `uses:` is permitted.
Widen policy first, start and inspect a canonical-coordinate canary, *then*
propagate the calls; see link:../../docs/compliance/repo-transfer-to-enterprise-playbook.adoc[the transfer playbook].
A zero-job `startup_failure` is not a passing check.

=== First-class alternative: fork-local reusable copies

If the effective policy cannot allow the cross-owner reusable, use the
link:https://github.com/hyperpolymath/MetaManifold-WebUI/blob/main/.github/workflows/hypatia-scan.yml[MetaManifold-WebUI pattern]:
copy each needed `workflow_call` implementation into the fork, then call it
locally with `uses: ./.github/workflows/<local-reusable>.yml`. The local copy
is reviewed and maintained by the fork; it is not a claim that the remote
reusable was permitted. Record the immutable upstream standards commit in each
copy, keep the `workflow_call` inputs/permissions, pin helper checkouts to that
same `metadatastician/standards` commit, and test the copy and any fork-specific
deltas. In a fork-local copy `job.workflow_sha` names the *fork's* commit, not
the standards source; replace it for every standards helper checkout with the
recorded upstream SHA. Actions checkout itself and any other cross-owner
reusables still need to be allowed by the caller's policy.

For example, replace the `deed`, `k9` and `hypatia` remote calls below with:

[source,yaml]
----
  deed:
    uses: ./.github/workflows/deed-conformance-reusable.yml
    permissions:
      contents: read
    with:
      require-files: true
  k9:
    uses: ./.github/workflows/k9-conformance-reusable.yml
    permissions:
      contents: read
      pull-requests: read
    with:
      require-files: true
      fail-on-indeterminate: false
  hypatia:
    needs: [fleet]
    if: ${{ always() }}
    uses: ./.github/workflows/hypatia-scan-reusable.yml
    permissions:
      actions: read
      contents: read
      security-events: write
    secrets:
      HYPATIA_SCAN_PAT: ${{ secrets.HYPATIA_SCAN_PAT }}
----

Apply the same local-copy treatment to the posting engine if that remote
reusable is refused. Preserve each lane's outputs, artifacts, event and
permission boundaries; the WebUI also intentionally avoids PR SARIF uploads,
a fork-specific choice that must not be silently applied estate-wide. Track
source-pin and contract drift in CI, refresh the copies deliberately, and test
that the local calls start jobs. If the fleet reusable is refused, use the
inline producer described in section 8.2.

=== Compatibility: optional previous-grid artifact

Do not add `pull-requests: read` to every caller of Hypatia. The reusable
retains its original permissions and accepts an optional
`previous-grid-artifact` input.

For a PR-revision comparison, a separate caller job with
`pull-requests: read` fetches the last trusted bot-authored Hypatia
comment and uploads `hypatia-grid-previous` containing `grid-previous.md`.
Pass that artifact name to Hypatia and declare a dependency on the job.
The canonical example is `.github/workflows/fork-governance.yml`.

Callers without this opt-in still run their scans; the comparison column
explicitly reports its missing PR baseline. The committed
`.hypatia-baseline.json` remains a different accepted-findings ledger.

== 2. The file

Copy this into `.github/workflows/fork-governance.yml` and replace `<SHA>` with
a standards commit. Do not use `@main`:

[source,yaml]
----
# SPDX-License-Identifier: MPL-2.0
name: Fork governance

on:
  pull_request:
  workflow_dispatch:

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

jobs:
  deed:
    name: DEED syntax
    uses: metadatastician/standards/.github/workflows/deed-conformance.yml@<SHA>
    permissions:
      contents: read
    with:
      require-files: true

  k9:
    name: K9-DEED conformance
    uses: metadatastician/standards/.github/workflows/k9-conformance.yml@<SHA>
    permissions:
      contents: read
      pull-requests: read
    with:
      require-files: true
      fail-on-indeterminate: false

  # Produces .gitbot-fleet/report-backs/*.json as the `fleet-report-backs`
  # artifact; the Hypatia lane downloads it before rendering. Pin a
  # gitbot-fleet commit. If your Actions policy refuses a reusable workflow
  # from another owner, use the inline form in section 8 instead.
  fleet:
    name: Fleet report-backs
    uses: hyperpolymath/gitbot-fleet/.github/workflows/fleet-report-back-reusable.yml@<FLEET-SHA>
    permissions:
      contents: read

  hypatia:
    name: Hypatia verdict grid
    # After the fleet job whatever its result: a dead fleet job renders as
    # orange fleet rows, never as a missing lane.
    needs: [fleet]
    if: ${{ always() }}
    uses: metadatastician/standards/.github/workflows/hypatia-scan-reusable.yml@<SHA>
    permissions:
      actions: read
      contents: read
      security-events: write
    secrets:
      HYPATIA_SCAN_PAT: ${{ secrets.HYPATIA_SCAN_PAT }}

  verdict:
    name: Post the fork governance summary
    needs: [deed, k9, hypatia]
    if: ${{ always() && github.event_name == 'pull_request' }}
    uses: metadatastician/standards/.github/workflows/fork-governance-reusable.yml@<SHA>
    permissions:
      contents: read
      actions: read
      pull-requests: write
    with:
      pr-number: ${{ github.event.pull_request.number }}
      deed-result: ${{ needs.deed.result }}
      k9-result: ${{ needs.k9.result }}
      k9-verdict: ${{ needs.k9.outputs.verdict }}
      hypatia-result: ${{ needs.hypatia.result }}
      hypatia-verdict: ${{ needs.hypatia.outputs.verdict }}
      hypatia-advisory: ${{ needs.hypatia.outputs.advisory }}
      canon-ref: <SHA>
----

The Hypatia reusable also accepts `hypatia-ref`, `panic-ref` and `pons-ref`
(40-hex SHA, or `HEAD` only for an intentional canary). Defaults are vetted,
not floating. Opt in with `hypatia-advisory: true` to include WF028 and other
below-threshold advisory findings in the JSON artifact and the separate
JSON-only advisory summary; this does not change SARIF or either gate.
The pinned CLI serialises WF028 as type `reusable_call_to_moved_repository`;
the grid labels that type `WF028` without altering the raw finding.

[NOTE]
====
The requested Hypatia pin also advances RE001's declared-egress checks. A
scanner pin does not enact the policy cutover: link:../../docs/decisions/ADR-009-declared-egress-for-secret-bearing-jobs.adoc[ADR-009]
remains proposed and D131 remains operative until the documented cutover.
Canary the new scanner against a consumer tree and review its full rule-set
changes rather than interpreting the pin as an egress waiver.
====

`canon-ref` tells the posting engine which standards commit to take the
renderer from. Pass the same `<SHA>` as the `uses:` pins: two refs that can
drift are two renderers that can disagree.

== 3. Remove the duplicate triggers

If the repository already calls a lane on `pull_request`, remove that trigger
from the lane's own workflow. Keep its `push` and `workflow_dispatch`
triggers. Otherwise every PR runs the same lane twice and, for Hypatia,
uploads the same findings to code scanning twice — which produces duplicate
alerts and two grids that can disagree.

[IMPORTANT]
====
This is the step people skip, and it is the step that produces the confusing
failure. The symptom is a PR with two "K9-DEED conformance" check runs, one
green and one orange, and no indication which one the comment is describing.
====

== 4. Settings

[cols="1,1,4",options="header"]
|===
| Setting | Value | Why
| Actions → General → Workflow permissions
| Read repository contents
| The workflows request exactly what they need per job; the repository default should not grant more.
| `HYPATIA_SCAN_PAT` (optional)
| fine-grained, read-only
| Lets the scanner read Dependabot, code-scanning and secret-scanning alerts. Without it the lane still runs on the built-in token and reports what it can see.
| Branch protection
| make the three lane jobs required, *not* the comment
| A comment cannot block a merge and must not appear to.
|===

== 5. Verify

. Open a pull request that touches nothing.
. You should get one comment, in this order: summary, k9-deed, Hypatia.
. Push another commit to the same PR. The comment must be *updated in place* —
   same comment id. If a second comment appears, the marker/author lookup is
   broken.
. Break something deliberately — add an unparsable `.deed` — and confirm the
   DEED row turns red and the summary with it.

== 6. Repositories with no DEED or K9 files

`require-files: true` fails the lane when there is nothing to check, which is
what you want in a repository that claims to be conformant. For a repository
that legitimately has no deeds yet:

* set `require-files: false` — the lane then reports grey (`not applicable`)
  rather than failing; or
* leave it `true` and add the file. A repository in this estate without a deed
  is a repository whose description is only in its README.

Grey is a deliberate, explicit state. It is never produced by accident: it
requires the lane to have run and to have decided that the question does not
apply.

== 7. Rollback

Delete `.github/workflows/fork-governance.yml`, and delete the bot's existing
comment. Nothing else is installed: the lanes are read-only, the posting engine
holds nothing, and no repository state is created on a branch.

An orphan comment left behind is worse than no rollout — it keeps claiming a
verdict on every new revision. Delete it.

[[fleet]]
== 8. The fleet report-backs

The Hypatia grid gives one row to every gitbot-fleet member the repository
enrols. The rows are only as good as the evidence behind them, and the
evidence is produced per run, never committed.

=== 8.1 The enrolment manifest

Create `.gitbot-fleet/enrolment.json`. State, for every member, whether it
applies to this repository, with a reason when it does not:

[source,json]
----
{ "schema": 1,
  "reporters": {
    "echidnabot":        { "enrolled": false, "gating": false, "reason": "no proofs in this repository" },
    "rhodibot":          { "title": "rhodibot (RSR compliance)", "enrolled": true, "gating": false },
    "panicbot":          { "enrolled": false, "gating": false, "reason": "panic-attack already reports in this lane directly" },
    "sustainabot":       { "enrolled": false, "gating": false, "reason": "reserved fleet slot; no adapter exists" },
    "glambot":           { "title": "glambot (presentation quality)", "enrolled": true, "gating": false },
    "seambot":           { "enrolled": false, "gating": false, "reason": "no seam register is declared" },
    "finishingbot":      { "title": "finishingbot (release readiness)", "enrolled": true, "gating": false },
    "cipherbot":         { "enrolled": false, "gating": false, "reason": "no cryptography is implemented" },
    "gsbot":             { "enrolled": false, "gating": false, "reason": "no general adapter is configured" },
    "accessibilitybot":  { "enrolled": false, "gating": false, "reason": "no served HTML surface" },
    "the-hotchocolabot": { "enrolled": false, "gating": false, "reason": "no comfort/DX adapter is configured" } } }
----

The example follows Hypatia Kin Arbiter priority (highest first); the grid sorts
fleet rows by that order regardless of manifest or artifact order. Fleet rows
are explicitly advisory (`"gating": false`). Do not enrol panicbot alongside
the direct panic-attack scan unless duplicate observations are intentionally
wanted: they are the same scanner. Per-row counts can double-count, and the
unique total can only corroborate findings with sufficient path, line and class
identity; it is not a licence to sum duplicate rows.

Enrol what is true of the repository, not what would look complete. A grey row
with a reason is honest; an orange row forever is noise. Changing the manifest
changes the grid's profile, so the next revision reads `— no comparable
baseline` once, which is correct: the question changed.

Also create `.gitbot-fleet/report-backs/` with a README saying the directory is
empty on purpose (the lane fills it at render time). The rsr-template-repo
carries both files.

=== 8.2 The producer job

With the reusable (repositories whose Actions policy allows a reusable workflow
from `hyperpolymath`): the `fleet` job in section 2. The reusable builds only
the enrolled adapters, caches the builds, runs gitbot-fleet's
`scripts/fleet-report-back.sh`, and uploads `fleet-report-backs`.

Inline (repositories under another owner, where a cross-owner reusable fails at
plan time with zero jobs and no error line): check out
`hyperpolymath/gitbot-fleet` at a pinned SHA with `actions/checkout`, run
`scripts/fleet-report-back-build.sh` and `scripts/fleet-report-back.sh`, and
upload the directory under the same artifact name. This repository's own
`.github/workflows/fork-governance.yml` is the worked example; copy its `fleet`
job.

=== 8.2a Existing repositories: the fixer

An existing repository need not be edited by hand. gitbot-fleet's
`scripts/fix-fleet-enrolment.sh <repo>` writes the manifest (only when absent,
enrolling what the tree shows), the report-backs README and the `fleet` job
(reusable form under the hyperpolymath owner, inline elsewhere), wires
`needs: [fleet]` into the `hypatia` job, and then checks that the standards
revision the workflow pins has the `report-backs-artifact` input. It exits 3,
not 0, until it does: run it in the same branch as the pin bump from
`scripts/propagate-workflow-pins.sh --fix --to <sha>`, so the producer and the
lane that reads it land together. New repositories inherit both from
`hyperpolymath/rsr-template-repo`. Details: gitbot-fleet `docs/REPORT-BACK.adoc`
§6.

=== 8.3 What the lane does with it

`hypatia-scan-reusable.yml` downloads the artifact named by its
`report-backs-artifact` input (default `fleet-report-backs`) into
`.gitbot-fleet/report-backs/` before rendering. A missing artifact is tolerated
and leaves the enrolled rows orange. Pass `report-backs-artifact: ""` to opt
out. The envelope contract is `docs/VERDICT-GRID-SPEC.adoc`; the producer is
documented in gitbot-fleet's `docs/REPORT-BACK.adoc`.

=== 8.4 Verify

Open a pull request. Each enrolled member's row should read a state other than
orange, or orange with a *reason* that names the member's own limitation
(for example echidnabot without an ECHIDNA engine). A row that still reads
"enrolled, but no report-back was received" means the artifact did not reach
the lane: check the `fleet` job's summary table and the lane's download step.
